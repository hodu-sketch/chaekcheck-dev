## 숫자 읽는 법

- 질문 하나에 카드 최대 8장. Sonnet이 질문×책마다 0~3점을 매긴 **같은 채점표**로 모든 안을 셈.
- **맞음%** = 카드 중 2~3점(주제가 맞음). **아주 맞음%** = 3점(주제와 조건 — 대상·쉬움·나라·장르 — 이 다 맞음). **틀린 카드** = 질문 하나에 보이는 0~1점 카드 수.
- **흔들림**: 같은 입력을 두 번 돌리면 아주 맞음 ±1~3%p, 틀린 카드 ±0.2장 → **3%p 이하 차이는 차이로 보지 않음**.
- **드는 것**: 2차 AI에 넣는 글자 수(비용 대용), 서버 메모리·시간, 만드는 데 든 작업.

| 칸을 후보 순위에 더하기 + 분명한 조건 거르기 (PFx, 2차 AI까지) | 아주 맞음 71 → 74%, 틀린 카드 0.47 → 0.39, 조건 질문 75 → 91% (넣음: v1.16.0 1차 ML에서 칸 보너스 0.004로 운영) | 2차 입력 그대로, 서버 1ms 안쪽 | [개선 보고서 6-4절](ai-search-improvement-2026-10-25.md) |

## 5. 1차 AI 호출을 작은 모델로 — [1차 호출 보고서](ai-search-first-call-models-2026-10-25.md) · [넣은 것과 뺀 것](ai-search-ml-first-call-decisions-2026-10-26.md)

v1.15까지 1차 호출(Haiku)은 질문을 읽고 검색어와 칸(분야·작은 칸·장르·대상 등)을 JSON으로 냈습니다(v1.16.0부터는 작은 신경망이 함). 이 중 「정해진 칸에서 고르기」를 LLM 없이 할 수 있는지, Sonnet이 만든 질문 3,000개(학습 2,306 / 시험 600)로 잼.

### 5-1. 칸 맞히기 (시험 600개, F1)

| 방식 | 큰 칸 | 작은 칸 99개 | 장르 | 분위기 | 드는 것 |
|---|---|---|---|---|---|
| TF-IDF + 로지스틱 회귀 | 73.7% | 38.2% | 28.6% | 72.7% | 수 MB, 1ms |
| KURE + 로지스틱 회귀 (첫 판) | 84.9% | 48.6% | 25.5% | 67.5% | 1MB + 이미 있는 KURE, 1ms |
| KURE + 칸마다 문턱 + 작은 신경망 | 89.6% | 79.2% | 65.8% | 83.7% | 같음 |
| 약한 칸 질문 3,000개 더 (학습 5,300개) | **90.7%** | **85.0%** | **71.6%** | **88.4%** | 같음 |
| Cross-Encoder (bge-reranker-v2-m3, 학습 없이, 시험 200개) | 37.5% | 43.5% | 22.9% | 54.7% | 질문 하나 9.2초(PC 16스레드) |
| Haiku (같은 지시문) | 93.4% | 87.6% | 82.8% | 92.0% | API, 1~2.4초 |

- 학습량에 따른 작은 칸(로지스틱 / 작은 신경망): 2,306개 79.2 / 78.5% → 4,306개 80.6 / 84.2% → 6,298개 81.6 / **86.5%**. 신경망은 4,000~5,000개에서 거의 다 배움([5-3절](ai-search-first-call-models-2026-10-25.md)).
- Cross-Encoder는 처음에 비교용으로 속도만 재고 정확도를 빠뜨렸다가 나중에 채움: 학습 없이는 TF-IDF보다 낮고 쌍마다 돌려 느림 → 운영 후보 아님([4-1절](ai-search-first-call-models-2026-10-25.md)).

### 5-2. 전체 흐름에 넣으면 (질문 57개, 2차 Haiku까지)

1차를 LLM 없이 신경망 칸 + 질문 낱말(+ 책 주제어)로 바꾼 안 M·MT: 두 번 돌린 평균 아주 맞음 **72 / 71.5%**, 틀린 카드 **0.36 / 0.35** — 그때 운영 P(72%, 0.37)와 같음. 책 찾는 질문에서는 1차 Haiku 호출(1~2.4초, 비용 약 15%)을 없애도 최종 카드가 나빠지지 않음([5-4절](ai-search-first-call-models-2026-10-25.md)).

### 5-3. 길 나누기 (책 찾기 아님 · 제목만 · 앞 책 가리킴 · 보통 질문 · 책첵 질문)

| | Haiku | 신경망 | 로지스틱 |
|---|---|---|---|
| 처음 (학습 질문에 이 유형이 1% 미만) | 97.8% | 58.5% | 37.0% |
| 유형마다 400개씩 고르게 다시 학습 | | **94.5%** | 93.5% |
| 책첵 질문 갈래 더해 5갈래(갈래당 600개, 운영 v1.16.0~) | | 94.6% | |
| 짧은 장르 질문(「판타지」) 300개를 더함 (짧은 질문 시험) | | 74 → **97.3%** (기존 시험 600개는 94.6 → 93.9%, int8 벡터 93.5%) | |

- 앞서 쓴 「98~100%」는 시험 600개 중 97%가 「아니오」라 늘 아니오만 해도 나오는 숫자였음 — 유형만 모아 다시 잼([5-5·5-6절](ai-search-first-call-models-2026-10-25.md)).

### 5-4. 속도와 비용 (같은 57개 질문, 같은 코드에서 설정만 바꿔)

| | 1차 Haiku | 1차 신경망 |
|---|---|---|
| 답 끝까지 중간값 / 느린 10% | 8.6 / 11.4초 | 8.1 / **9.7초** |
| 입력 토큰 (1차 + 2차) | 7,621 | 6,365 |
| 검색 1,000번 | $1.52 | **$1.40** (−8%) |

시간 대부분은 2차 Haiku라 중간값은 0.5초만 줄고, 1차 Haiku가 늦던 검색이 줄어 느린 쪽이 1.7초 줄어듦([결정 기록 3-5](ai-search-ml-first-call-decisions-2026-10-26.md)).

### 5-5. 운영 뒤 고친 것: 이어 묻는 질문

v1.16.0을 쓰다 사용자가 찾음: 「판타지인데 → 좀 슬프고 서정적인거」가 이어지지 않음. 원인은 「새 주제 규칙」이 이어 묻는 질문 171개 중 47번 잘못 켜진 것 → 앞·지금 질문 벡터로 관계 7가지(앞 책 안에서 · 한 권 묻기 · 조건 더하기 · 주제 옮기기 · 결과에 반응 · 새 주제 · 책 찾기 아님)를 나누는 신경망(시험 700쌍 96.4%)으로 바꿈.

| 실제 대화 80개, 2차 Haiku까지, 3번씩 | 규칙 (v1.16.0) | 관계 분류기 (v1.16.1) |
|---|---|---|
| 맞음 평균 (폭) | 74.3% (72.2~76.4) | 76.2% (75.4~76.5) |
| 조건 더하기(continue) 맞음 | 67.4% | **76.2%** (3번 모두 위) |
| 카드 없는 답 (70문) | 12~14 | **7~9** |

- 전체 차이(+1.9%p)는 규칙 쪽 흔들림(4.2%p) 안 — 처음 한 번 돌렸을 때 쓴 「72.2 → 75.4%」는 차이를 크게 보였던 숫자라 바로잡음([3-5](ai-search-ml-first-call-decisions-2026-10-26.md)). 흔들림을 넘는 것은 조건 더하기와 빈 답.

## 6. 운영에서 사용자가 찾은 문제 고치기

사용자가 운영에서 직접 찾은 사례를 그대로 시험으로 만들고, 고친 뒤 같은 시험과 기존 시험(회귀 확인)으로 다시 잼.

| 찾은 것 | 원인 | 고친 것 | 전 → 후 |
|---|---|---|---|
| 「ai agent나… → llm인가 → 위에 언급한 두 개에 관한 책」에 프롬프트 엔지니어링 책 | 「앞 책 가리킴」 후보가 바로 앞 턴 책 2권 + 이웃뿐, 앞 질문 둘을 함께 보지 않음 | 앞 턴들의 책도 후보로 (v1.16.2), 앞 질문 여럿을 이어 씀 (v1.16.3) | v1.16.2로는 그대로, v1.16.3에서 AI 에이전트 책과 LLM 책이 함께 나옴 |
| 시기를 묻지 않았는데 「2026년 기준 최신 책은 찾기 어렵지만」 | 2차에 준 출간 연도를 늘 씀 | 시기를 물을 때만 (v1.16.2) | 시기 말을 꺼낸 답 16개 중 1 → 0 |
| 「판타지 → 추리 → 두 개 섞은 느낌」에 카드 1장 | 관계 분류기는 바로 앞 질문만 봄 | 「두 개」·「둘 다」·「섞은」이면 앞 질문 여럿을 이어 씀 (v1.16.3) | 6장, 판타지와 추리가 섞인 소설 |
| 「…입문서지만 전문적」 → 「수학적인 것도 좀」에 「수식보다 실습 중심」 책 | 2차가 조건과 반대인 책도 주제만 맞으면 넣음 | 반대인 책은 빼고 앞 조건 지키기, 조금만 채우면 그만큼만 말하기 (v1.16.3) | 3번 모두 반대인 책 0권, 5권씩 |

**3번 이어지는 대화 50개** (Sonnet이 씀, 세 번째 질문의 카드를 Sonnet 채점, [3-6](ai-search-ml-first-call-decisions-2026-10-26.md))

| | v1.16.2 | v1.16.3 |
|---|---|---|
| 앞 주제 둘 합치기 25개: **카드 0장** | **12개** | **1개** |
| 마지막 질문만 잇기 15개 (「두 권만」·「둘 중에」 같은 헷갈리는 말 포함): 맞음 / 틀린 카드 | 85% / 0.73 | **92% / 0.40** |
| 보인 책 가리키기 10개: 맞음 | 69% | **87%** |
| 기존 이어 묻는 대화 80개(회귀 확인): 맞음 | 75.4~76.5% | **79.6%** |

- 합치기 신호 말은 합치기 25개 중 22개에 걸리고 나머지 25개에는 하나도 안 걸림. 못 잡은 3개는 두 주제를 직접 말한 것이라 질문 낱말로 찾음.

## 7. 2차를 에이전트로 — [에이전트 보고서](ai-search-agent-2026-10-26.md)

2차(후보 30권에서 고르기)를 한 번의 호출 대신, 도구 `answer`·`search_again`(맞는 책이 없으면 새 낱말로 한 번 더 찾기)·`ask_user`(두 갈래로 읽히면 되묻기, 화면에 버튼)를 쓰는 Haiku로 만들어 봄. 새 질문 72개(애매한 질문, 애매하게 이어 묻기, **3턴 「앞 주제 둘 합치기」**, 책이 적은 주제, 분명한 질문), 되물으면 가상 사용자(Haiku)가 숨긴 「원한 책」에 맞춰 답함, Sonnet 채점, 방식마다 두 번 돌린 평균.

| 기준선 | 방식 | 맞음 | 맞는 카드/질문 | 틀린 카드/질문 | 0장(72개 중) | 첫 글 | 검색 1,000번 |
|---|---|---|---|---|---|---|---|
| v1.16.2 | 한 번의 호출 | 72.5% | 3.8 | 1.42 | 14.5 | — | — |
| v1.16.2 | 에이전트 / 3권 미만이면 다시 찾기 (한 번씩) | 80.2 / 82.4% | 4.7 / 4.9 | 1.15 / 1.04 | 5 / 5 | — | — |
| **v1.16.3** | 한 번의 호출 | 77.0% | 4.0 | 1.19 | 9.5 | **5.1초** | **$1.40** |
| **v1.16.3** | 에이전트 / 3권 미만이면 다시 찾기 | 77.9 / 80.1% | 4.4 / 4.6 | 1.24 / 1.15 | 7.5 / 9.0 | 9.4 / 9.8초 | $1.85 / $1.96 |

→ 처음(v1.16.2)에는 에이전트가 8~10%p 이겼고 합치기는 맞는 카드가 1.5 → 4.9장. 그런데 같은 날 한 번의 호출에 「앞 질문들을 함께 찾는」 규칙을 더한 v1.16.3이 나와([3-6](ai-search-ml-first-call-decisions-2026-10-26.md)), 그 위에서 다시 재니 **차이가 흔들림(±5%p) 안으로 줄고**, 첫 글은 두 배 늦고, 돈은 32~40% 더 듦 → **켜지 않음**. 남은 이득은 합치기·이어 묻기(합치기 맞는 카드 2.7 → 4.2, 3권 미만 방식). 분명한 질문에서는 네 번 모두 되묻기 0번. **배운 것: 기준선이 바뀌면 다시 잰다 — 처음 숫자로 내보냈다면 비용만 늘었을 것.**

**그래서 되묻기만 한 번의 호출에** (고르기 JSON 맨 앞에 `ask` 칸, [보고서 10절](ai-search-agent-2026-10-26.md)): 전체 맞음 77.0 → 79.6%, **애매한 질문 69.4 → 77.8%, 맞는 카드 4.2 → 5.6장**, 분명한 질문 되묻기 0번, 되묻지 않은 질문의 첫 글 5.1 → 5.4초·비용 +3%. 에이전트에서 쓸모 있던 한 가지만 가장 싼 자리로 옮긴 것.

**운영에 넣은 조합 (v1.17.0)** — 되묻기 + Haiku 생각 끄기 + 프롬프트 캐싱, 10만 권 위 두 번 평균([보고서 11절](ai-search-agent-2026-10-26.md)): 맞음 78.0 → **80.6%**, 애매한 질문 66.7 → **78.8%**, 틀린 카드 1.32 → **1.02장**, **첫 글 4.0 → 2.3초**, 출력 토큰 절반. 응답 시간을 단계별로 재 보니 검색은 0.45초뿐이고 나머지가 Haiku의 「생각」이라는 데서 출발. 생각을 꺼도 부정어·조건 질문(57문항 종류별)은 그대로였고, 대가는 카드 수(질문당 6.7 → 5.8장). 72문항 묶음 중 합치기는 87.6 → 72.5%, 책이 적은 주제는 66.7 → 56.6%로 내려감(묶음 12~15개라 흔들림이 크지만 남은 일).

## 8. 책을 10만 권으로

v1.17.0에서 AI 검색 대상을 보유 도서관 많은 순 10만 권(소개 있는 76,759권, 책 벡터 81,078권)으로 넓힘. 사용자가 「검색 결과 책이 줄어든 느낌」을 말해 확인:

| | 27,227권 | 76,759권 |
|---|---|---|
| 같은 질문 72개, 같은 코드(v1.16.3): 질문당 카드 | 5.19 / 5.12장 (두 번) | 5.35장 |
| 같은 질문 72개: 카드 0장 | 11 / 8개 | 6개 |
| 책 벡터 비교 시간 (질문 하나) | 84ms | 224ms |

- 책이 늘어 카드가 줄지는 않음. 운영 기록에서 질문당 카드가 6.1(v1.15) → 5.1(v1.16.0~2) → 4.8(v1.16.3)장으로 준 것은 10만 권 전부터이고, 2차가 「맞는 책이 적으면 적게 고르기」로 엄해진 영향으로 봄 [추론] — 운영 질문은 그때그때 달라(구간마다 11~42번) 참고만. v1.17.0의 생각 끄기도 카드를 질문당 6.7 → 5.8장으로 줄임([에이전트 보고서 11절](ai-search-agent-2026-10-26.md)).

## 9. 규칙 전체 점검과 되묻기 v2 (v1.18.0) — [규칙 점검](ai-search-rules-2026-10-27.md)

**출발점**: v1.17.0 뒤 사용자가 「사진」에 되묻지 않는 것, 되묻기에 버튼 대신 직접 쓴 답(「그림」 → 「인상주의」)을 찾음. 재 보니 생각을 끈 뒤로 애매한 질문 30개에서 되묻는 수가 8~9개 → 5~6개로 줄어 있었는데, 맞음·속도만 보던 측정에서는 드러나지 않았음.

**어떻게 쟀나**: 2차 단계를 정하는 규칙 29개(지시문 20줄, 코드 9곳)를 출처와 함께 한 표에 모으고, 규칙마다 그것을 확인하는 문항을 붙인 **80문항 규칙 시험**을 만듦(지시문 예시에 없는 낱말로, 되묻기·금지 표현은 자동 판정, 카드는 Sonnet 채점). 고친 판과 운영 판을 두 번씩 돌린 평균.

| 문제 | 원인 | 고친 방법 | 결과 (운영 → v2) |
|---|---|---|---|
| 「사진」, 「음악」처럼 뜻이 여럿인 한 낱말에 되묻지 않음 | 생각을 끈 Haiku는 질문만 보고 「흔한 뜻」으로 골라 버림. 갈래가 갈리는지 볼 근거가 없음 | 2낱말 이하 질문에는 후보 30권의 큰 분야 수를 「후보 분야: 예술·취미 9권, 여행 7권…」 한 줄로 함께 줌(책 프로필에서 셈, 코드 C4) | 되묻기 **3/32 → 30/32** |
| 되묻기에 버튼 대신 직접 쓰면 그 말만으로 찾음 | 직접 쓴 답이 그냥 「다음 질문」이라, 관계 분류기가 「새 주제」로 보면 앞 질문(「그림」)을 버림. 모델은 자기가 되물었다는 것도 모름 | 웹이 앞 대화의 되묻기 턴에 「되물은 말·고를 답」을 실어 보내고, 서버는 그 다음 질문을 늘 앞 질문과 이어 붙여 찾음(합치기와 같은 길). 모델에게 「되물은 말」을 보여 주고 그 턴엔 되묻지 않음 | 직접 답한 뒤 카드 맞음 **48 → 96%** |
| 되물은 말의 뜻이 모델에 전해지지 않음(점검에서 찾음) | 그 설명이 되묻기용 지시문에만 있었는데, 되묻기 다음 턴에 코드는 다른 지시문을 보냄 — **죽은 지시문** | 설명을 늘 쓰는 지시문으로 옮기고 중복 줄을 뺌 | 위 96%에 포함 |
| 생각을 끈 뒤 카드가 줄어듦 | 생각 없이 고르면 덜 확실한 책을 빼는 쪽으로 기움 | 「맞는 책이 여럿이면 8권까지 채운다(조건과 반대인 책으로는 안 채움)」 — 「억지로 고르지 않는다」와의 경계를 문장으로 정함 | 분명한 질문 맞는 카드 **5.9 → 7.0장**, 대신 틀린 카드 0.17 → 0.43장 |
| 되물을 때 고를 답만 내밂 | 지시문에 다른 답을 받는다는 안내가 없음 | 「원하는 게 따로 있으면 적어 달라」는 뜻을 모델이 질문에 맞는 말로 덧붙이게 함 | 그런 말이 든 되묻기 **5/18 → 51/63** |
| **전체** | | | 카드 맞음 **76 → 92%**, 틀린 카드 **1.29 → 0.39장**, 첫 글 1.8 → 1.9초(그대로) |

- **대가**: 강아지·요가·캠핑 같은 흔한 낱말에도 20번 중 9번 되물음(운영 3번). 「뜻이 하나인 이름은 되묻지 않기」를 더한 v3는 되묻기를 조금 줄였지만 카드 맞음이 88%로 낮아 되돌림.
- **지켜지지 않는 규칙도 숫자로 드러남**: 「한 줄을 그대로 옮기지 않는다」는 모든 판에서 카드의 62~64%가 한 줄과 20자 넘게 같음(한 줄은 Haiku가 만든 글이라 저작권 문제는 아님) → 규칙을 바꿀지 결정할 일. 「묻지 않은 출간 시기」는 지시문을 콕 집어도 7~9번 그대로.
- effort `medium`은 `low`와 맞음 92% / 92%로 같고 출력 토큰만 8% 많아 `low` 유지.

## 10. AI 검색 표 줄이기 (v1.18.0) — [운영 기록 11절](../maintenance/6-aisearch.md)

**출발점**: 사용자가 짚은 비효율 둘 — 넣기 뒤 빈 공간이 남음, 도서관 번호 칸이 가장 큼. 실제 표의 복사본(76,759권)으로 전후를 쟀더니, 예상한 곳 말고 **더 큰 원인**이 나옴.

| 문제 | 원인 | 고친 방법 | 결과 (전 → 후) |
|---|---|---|---|
| 글 칸의 통계(ANALYZE)가 칸마다 약 200초, 운영에서 10만 권을 넣은 뒤 자동 ANALYZE가 15분 동안 CPU를 씀(재다가 찾음) | DB 정렬 규칙이 `en_US.utf8`이라 긴 한국어 글을 정렬해 통계를 만드는 데 오래 걸림. 이 칸들은 사람에게 정렬해 보이지 않고 낱말 검색(LIKE + pg_bigm)에만 씀 | 한 줄·검색 글 칸만 `C` 정렬 규칙으로(Liquibase changeset, 검색 결과는 같음) | 칸 ANALYZE **약 200초 → 1초**, 표 전체 **약 400초 → 6초** |
| 넣기 뒤 지운 줄 자리가 빈 공간으로 남음 | 넣기가 「전부 지우고 다시 넣기」 | 넣기 끝에 `VACUUM (FULL, ANALYZE)` — 정렬 규칙을 고친 덕에 10초 | 넣은 직후 216MB → **113MB**, 정리 **10초**(그동안 AI 검색 대기) |
| 도서관 번호 칸이 가장 큼(약 90MB 중 42MB) | 책마다 평균 79개 번호를 8바이트(bigint)로 | 4바이트(integer)로(가장 큰 번호 2,681) | **42 → 25MB** |
| **표 + 인덱스** | | | **188 → 115MB (−39%)** |

- **검색 속도는 빨라지지 않음**: 「소설」 140 → 141ms, 「기후 위기」 40 → 34ms. 표가 메모리에 있어 시간은 읽는 양이 아니라 LIKE 계산이 정함. 「네 낱말」 검색은 표를 정리한 뒤 실행 계획이 바뀌어 12 → 41ms로 느려짐(정리만 한 표에서도 같음) — Haiku의 몇 초에 비하면 작지만 운영 로그 `keyword` 단계로 지켜볼 일.
- 예상한 이득(빈 공간을 함께 읽어 느림)은 숫자로 나오지 않았고, 재다가 찾은 정렬 규칙 문제가 실제 이득.

## 11. 첫 글 시간 줄이기 (v1.19.0) — [첫 글 시간](ai-search-latency-2026-10-27.md)

**출발점**: 답을 SSE로 흘리므로 사용자가 기다리는 것은 첫 글. 운영 로그의 단계별 시각으로 쪼개 보니 요청 → Haiku 첫 토큰이 약 1.91초, 그중 Haiku 앞의 준비가 약 0.57초였고, 그 안의 낱말 검색(176ms)과 표지·요약 읽기는 앞 단계를 기다릴 이유가 없는 일이었음.

**먼저 Haiku 쪽을 따로 잼**(같은 지시문·후보로 Haiku만 15번씩): 바닥값 0.77초, 입력을 줄이거나 캐싱을 꺼도 첫 토큰은 그대로, 형식 강제가 +0.25~0.4초, 되묻기 칸이 head를 0.05초(느린 10%는 0.6초) 늦춤 → 프롬프트 줄이기는 하지 않고, **기다림을 겹치는 쪽**으로.

| 문제 | 원인 | 고친 방법 | 결과 (v1.18.0 → 고친 판) |
|---|---|---|---|
| 낱말 검색이 질문 벡터·1차 신경망·이웃 뒤에야 시작 | 계획(낱말)이 1차 신경망에서 나온다고 보고 순서대로 짬. 그런데 첫 질문의 낱말은 질문만으로 정해짐 | 질문 벡터를 만들 때 낱말 검색을 같이 시작, 계획의 낱말이 같고 뺄 책이 없을 때만 그 결과를 씀(후보는 전과 같음) | 5낱말 이상 첫 질문의 낱말 검색 대기 **102 → 0ms**(40번 중 36번 이미 끝남) |
| 표지·AI 요약을 다 읽은 뒤에 Haiku를 부름 | 카드 재료를 한곳에서 한꺼번에 읽음. 둘은 Haiku 프롬프트에 안 들어감 | 한 줄·연도만 읽고 Haiku를 부르고, 표지·요약은 그동안 읽어 첫 카드 때 받음 | 요청 → Haiku 호출 **417 → 316ms**(1안과 합친 값) |
| 되묻지 않을 질문도 빈 되묻기 칸부터 씀 | 되묻기를 켜면 모든 질문에 되묻기 형식(ask가 head 앞) | 되묻기 형식은 4낱말 이하 첫 질문·이어지는 질문에만 | Haiku 첫 토큰 → 첫 글 **108 → 20ms**, 느린 10% **199 → 28ms** |
| **5낱말 이상 첫 질문** | | | 첫 글 **1.68 → 1.43초**, 느린 10% **2.15 → 1.75초** |
| **전체** | | | 첫 글 1.84 → 1.69초, 카드 맞음 **91 → 92%**, 틀린 카드 0.42 → 0.41장(그대로) |

- **운영에서 (같은 첫 질문 24개, 배포 전후)**: 5낱말 이상 첫 질문 첫 글 **2.63 → 2.06~2.25초**(v1.19.0 두 번), Haiku 호출까지 준비 505 → 302~356ms, 서버 첫 토큰 → 사용자 첫 글 741 → 504~533ms. 로컬(−0.25초)보다 크게 준 것은 운영의 낱말 검색·카드 읽기가 더 느려 겹친 몫이 컸기 때문([첫 글 시간 6절](ai-search-latency-2026-10-27.md)).
- 짧은 질문(4낱말 이하)은 되묻기를 지키려고 그대로 둠. 되물을 때 첫 글은 되묻는 말이 다 써진 뒤라 2.4초대.
- 가장 큰 남은 몫인 형식 강제(+0.25~0.4초)는 JSON이 깨지는 비율을 재기 전에는 빼지 않음.

## 12. 대화 점검과 다음 계획 (계획, 사이클 26 뒤) — [대화 점검](ai-search-talk-review-2026-10-28.md)

**출발점**: 사용자가 직접 써 보니 「우리가 손으로 바꾼 문구가 어색함」, 「책 정보만 하나하나」, 「대화가 어색함」. 운영과 같은 설정의 로컬 서버에 일상 말·엉뚱한 말·이어 묻기를 섞은 **대화 37개(57턴)**를 보내고, 코드에서 모델 글이 그대로 보이지 않는 곳을 줄 번호까지 찾음.

| 찾은 것 | 숫자 | 원인 | 고칠 안 |
|---|---|---|---|
| 모델이 잘 쓴 머리말을 웹이 지우고 「맞는 책을 찾지 못했어요」로 | 57턴 중 **5턴** | 고른 책이 0권이면 웹이 머리말을 숨김 | 모델 글을 그대로 두고, 고정 문구는 빈 머리말일 때만 |
| 책 밖 말에 대화와 상관없는 고정 되묻기 | **6턴**(「잠이 안 와」에 「경제 교양서」 예시) | 모델을 부르지 않는 고정 문구 + 무작위 예시 | 짧은 모델 호출 하나로 답하고 대화에 맞춘 예시로 책 이야기에 이끌기 |
| 「직접 적어 주세요」가 두 번 | 모델 되묻기 **11턴 전부** | 모델 질문 + 웹 힌트가 같은 말 | 웹 힌트 빼기 |
| 1차가 잘못 나눔 | 「로그인 어떻게 해?」·「잠이 안 와」·「작가가 누구야?」·「영화 추천해줘」 | 길 나누기 학습 질문에 없는 꼴 | 학습 질문 더해 다시 학습(지금 94.6%) |

## 13. 배운 것

- **기준선이 바뀌면 다시 잰다.** 에이전트는 v1.16.2 위에서 8~10%p 이겼지만, 같은 날 한 번의 호출을 고친 v1.16.3 위에서는 흔들림 안이었음. 처음 숫자로 내보냈다면 비용만 늘었을 것.
- **한 번 돌린 차이는 믿지 않는다.** 「72.2 → 75.4%」는 3번씩 다시 돌리니 흔들림 안(74.3 vs 76.2%)이었고, 흔들림을 넘는 것(조건 더하기 67 → 76%)만 남김.
- **잘한 것처럼 보이는 숫자를 의심한다.** 길 나누기 「98~100%」는 늘 「아니오」만 해도 97%가 나오는 칸이었음 → 유형별로 다시 잼.
- **채점자도 잰다.** Sonnet 점수를 Opus로 다시 매겨 맞음/틀림 88% 일치, Opus가 조금 후함 → Sonnet 점수는 부풀려지기보다 엄한 쪽.
- **시험 도구도 틀릴 수 있다.** 카드 글은 스트림의 다른 이벤트로 와서, 한동안 「글에 연도를 썼는지」를 머리말로만 셌음 → 고치고 다시 확인해 기록에 남김.
- **지표에 없는 것은 나빠져도 모른다.** 생각 끄기는 맞음·속도로만 재서, 되묻기가 줄어든 것을 사용자가 「사진」으로 찾을 때까지 몰랐음 → 규칙마다 판정 칸을 두는 규칙 시험을 만듦.
- **규칙은 코드 경로와 함께 읽는다.** 지시문만 보면 멀쩡했지만, 그 줄이 쓰이는 턴에 코드는 다른 지시문을 보내고 있었음(죽은 지시문).
- **재 보면 원인이 다른 곳에 있다.** 「빈 공간을 읽어서 느리다」는 예상 대신, 재다가 「정렬 규칙 때문에 통계가 400초」를 찾음. 줄인 크기는 검색 시간을 바꾸지 못했음.
- **사용자가 찾은 사례를 시험으로 만든다.** 6절의 네 가지는 모두 운영에서 사용자가 찾은 것이고, 같은 꼴의 질문 50개로 늘려 고친 전후를 잼.

## 14. 한계 (포트폴리오에 같이 쓸 것)

- 질문 57개, 한 사람이 만든 질문. 채점은 사람 대신 Sonnet(같은 채점표를 모든 안에 씀).
- 대부분 안은 한 번씩만 돌림. 흔들림 폭(±3%p)은 두 안을 두 번 돌려 잰 값.
- 「○○ 같은 책」은 9개뿐이라 숫자가 크게 흔들릴 수 있음.
- 채점자 확인은 사람이 아니라 다른 모델(Opus)로 함: 카드 100장에서 맞음/틀림이 Sonnet과 88% 같음(Opus가 조금 후함). 사람이 직접 본 점수는 없음.
- 이어 묻는 질문 시험(대화 80개)은 rule·relation을 3번씩 돌림: 전체 맞음의 폭이 4%p 안팎이라 2%p 차이는 「비슷함」으로 읽어야 함. 관계마다 10~20개라 칸마다는 더 흔들림.
- 속도·비용은 로컬 PC에서 잰 값(2차 Haiku는 실제 API). 운영 앞뒤 값은 질문이 서로 달라 참고만.
- 3번 이어지는 대화(「위에 말한 두 개」, 「둘 섞은 느낌」)는 운영에서 사용자가 찾은 뒤 50개 시험을 만들어 고침(합치기 카드 0장 12 → 1 / 25, [3-6](ai-search-ml-first-call-decisions-2026-10-26.md)). 한 번씩 돌린 값이고, 「앞 질문 여러 개」는 신호 말 규칙으로 잡음(모델 아님).
- 에이전트 시험(7절)은 방식마다 두 번 돌림: 같은 한 번의 호출이 73.5 / 80.5%로 흔들려 5%p 안팎은 「비슷함」. 묶음마다 10~20개라 묶음 숫자는 더 흔들림(합치기 56 / 65%). 되묻기 답은 가상 사용자(Haiku)가 함 — 실제 사람이 되묻기를 어떻게 느끼는지는 재지 않음.
- 규칙 시험(9절)의 「되물어야 한다 / 되묻지 말아야 한다」 기대값은 한 사람이 정함. 「강아지」처럼 갈래가 실제로 있는 말은 되묻는 편이 맞을 수도 있음. 판마다 두 번만 돌렸고 묶음마다 2~16문항이라 묶음 숫자는 크게 흔들림.
- 표 줄이기(10절)는 로컬 PC의 복사본에서 잼. 운영 서버(ARM 2코어)의 ANALYZE 시간은 로그의 시작·끝 시각(15분)으로만 확인함.
