# 책이 20만·50만·100만 권이 될 때 가까운 책 찾기 (2026-10-30)

AI 검색 책을 늘릴 계획(사용자: 다음은 20만 권, 그 뒤로도 점점 늘림)에 맞춰, 「가까운 책」 단계(`BookVectorFile.nearest`)를 어떻게 키울지 정리한 기록입니다. [HNSW 보고서](2026-10-29-hnsw.md)의 잰 값을 이어 쓰고, 이번에 **binary·int4로 먼저 거르는 방식의 재현율**과 **A(Java 깔때기)의 속도**를 새로 쟀습니다. 잰 값과 추정을 나눠 적고, 추정에는 [추정]을 붙였습니다.

사용자 결정(2026-10-30): "A. Java 깔때기 (전부 훑기 + 다시 매기기)로 개발해줘" → 서버 코드로 넣음(8절, 설정 `chaekcheck.aisearch.vector.search.mode: funnel`). 운영 배포는 아직입니다.

## 0. 결론 먼저

- 지금 방식(int8 전수 비교)은 **15만~20만 권까지** [추정, HNSW 보고서 0절]. 50만 권부터는 시간(운영 약 0.5~1초)과 힙(0.5~1GB, -Xmx640m 초과) 둘 다 넘칩니다.
- 그다음 길은 4가지(2절 A~D). **추천: A(Java 깔때기)로 시작하고, 그것도 넘치면 D(전용 벡터 DB)**.
  - A는 지금 파일(`book-vectors.bin`)과 코드 구조를 그대로 살리고 RAM이 가장 작습니다(100만 권 binary 128MB).
  - 81,078권에서 잰 재현율: 해밍 1만 → 비대칭 binary 2,000 → int8 다시 매기기로 상위 120권의 **99.2%**를 찾습니다(3절).
  - **A의 Java 속도(잰 값, PC)**: 81,078권 79.8 → **6.9ms**, 20만 권 190.9 → **10.2ms**, 50만 권 484.8 → **21.9ms**, 100만 권 715.7(HNSW 보고서) → **32.0ms**. 힙은 binary 비트만이라 100만 권 약 135MB(지금 방식 약 1,036MB)(7절).
  - 아직 안 잰 것: 책이 늘 때 같은 재현율을 지키려면 1·2단계에서 몇 권을 남겨야 하는지(5절).
- B(halfvec HNSW)가 메모리를 많이 먹는 이유는 「HNSW라서」보다 **색인 안에 halfvec(2KB)를 넣어서**입니다(4절). binary를 넣은 HNSW(C)는 A와 비슷한 크기로 내려옵니다.
- 벡터 찾기를 인터페이스 하나 뒤에 두면(지금 `KureQuestionVectors.nearest`) A→D로 바꿀 때 나머지 흐름은 그대로입니다. 나중에 MSA로 가면 벡터 검색을 따로 떼기에도 맞습니다.

## 2. 네 가지 길

모두 「거칠게 많이 거르고, 남은 것만 정확하게 다시 매긴다」는 틀은 같습니다. 다른 점은 **무엇을 RAM에 두는가**와 **후보를 어떻게 찾는가(전부 훑기 / 그래프 따라가기)**입니다.

| 길 | 구조 | RAM (100만 권) | 장점 | 약점 |
|---|---|---|---|---|
| **A. Java 깔때기** | binary 해밍으로 전부 훑기 → 비대칭 binary → int8 다시 매기기 | 약 128MB + 파일 캐시 | 새 인프라 없음, 정확도는 지금과 거의 같게 맞출 수 있음 | 1단계가 책 수에 비례, 직접 짜는 코드 |
| B. pgvector halfvec HNSW | DB 안 근사 검색 | 색인 약 2.7GB가 캐시에 있어야 함 | 표준 방식, SQL로 끝 | DB 서버 RAM 8GB급 [추정], 재현율 0.87 (81k 잰 값) |
| C. pgvector binary HNSW + 다시 매기기 | pgvector README 방식 | 색인 약 0.3~0.5GB [추정] | DB 메모리 작음 | 손해가 두 번(대칭 해밍 + HNSW 근사), 재현율 안 잼 |
| D. 전용 벡터 DB (예: Qdrant) | binary 양자화 + 디스크 원본 + 다시 매기기가 기본 기능 | 작음 | 깔때기를 직접 안 짬 | 서버·동기화·백업이 하나 더 생김 (프로젝트 규칙상 따로 결정) |

### A. Java 깔때기 (전부 훑기 + 다시 매기기)

저장:
- RAM: 책마다 **binary 벡터** 하나. 1,024개 숫자의 부호(+면 1, 아니면 0)만 남긴 128바이트(`long` 16개).
- 디스크: 지금의 int8 + scale 파일(책당 1KB) 그대로. 필요한 줄만 읽습니다(메모리 매핑이나 위치 지정 읽기).

검색 순서:
1. **해밍 거리로 전부 훑기** → 상위 N1권(예: 1만). 질문도 부호만 남겨 binary로 만들고, 책마다 XOR 뒤 1의 개수를 셉니다(6절).
2. **비대칭 binary** → N1 중 상위 N2권(예: 2,000). 질문은 원래 소수 그대로, 책은 비트에 따라 +1/−1로 보고 내적합니다. 1단계와 같은 128바이트를 쓰므로 메모리가 더 들지 않습니다. 질문 쪽 정보를 버리지 않아 해밍보다 정확합니다(3절).
3. **int8 다시 매기기** → N2권의 int8 줄만 파일에서 읽어(2,000 × 1KB = 2MB) 지금과 같은 점수 `(Σ int8 × q) × scale`로 상위 120권.

성격: RAM이 가장 작고 최종 점수는 지금과 똑같습니다. 대신 1단계가 **모든 책을 매번 훑어** 시간이 책 수에 비례합니다.

### B. pgvector halfvec HNSW

- 저장: 표에 `halfvec(1024)`(숫자 하나 16비트, 책당 2KB) + `USING hnsw (embedding halfvec_ip_ops) WITH (m = 16, ef_construction = 64)`.
- HNSW 구조: 맨 아래층에는 모든 책이 있고 책마다 가까운 이웃 약 32권(2 × m)과 연결됩니다. 위층으로 갈수록 일부 책만 있어, 멀리 빨리 가는 고속도로 역할을 합니다.
- 검색: 맨 위층의 시작점에서 「이웃 중 질문에 더 가까운 쪽으로 이동」을 반복하며 한 층씩 내려갑니다. 맨 아래층에서는 후보 `hnsw.ef_search`(예: 200)개를 유지하며 주변을 훑습니다.
- 잰 값(81k, HNSW 보고서 3절): 색인 211MiB, DB 시간 11.6ms, 재현율 0.869(k 120, ef_search 200). 색인이 메모리에 다 있지 않으면 80~220ms.
- 성격: 책 대부분을 보지 않아 시간이 거의 늘지 않지만, **색인 전체가 RAM에 있어야** 하고 근사라 놓치는 책이 생깁니다.

### C. pgvector binary HNSW + 다시 매기기

B와 같은 그래프인데 색인 안에 halfvec 대신 binary(128B)를 넣습니다.

```sql
CREATE INDEX ON book_half USING hnsw ((binary_quantize(embedding)::bit(1024)) bit_hamming_ops);

SELECT id FROM (
  SELECT id, embedding FROM book_half
  ORDER BY binary_quantize(embedding)::bit(1024) <~> binary_quantize(:q)   -- 해밍, 2,000권
  LIMIT 2000
) t ORDER BY embedding <#> :q LIMIT 120;                                    -- 원본으로 다시 매기기
```

- 색인은 작고, 원본 halfvec는 표(디스크)에서 2,000줄만 읽습니다.
- 손해가 두 번입니다. (1) `bit_hamming_ops`는 대칭 해밍만 되고 A의 2단계(비대칭)를 넣을 수 없습니다. (2) HNSW 자체가 근사입니다. 재현율은 아직 재지 않았습니다.

### D. 전용 벡터 DB (예: Qdrant)

- 별도 서버. 컬렉션 설정으로 binary 양자화 벡터는 RAM(`always_ram`), 원본은 디스크(`on_disk`), 후보를 넉넉히 뽑아 원본으로 다시 매기기(oversampling + rescore)를 씁니다. **A의 깔때기 위에 HNSW 그래프를 얹은 것을 제품으로 만든 것**입니다.
- 직접 짤 코드는 적지만, 프로세스 하나 + PostgreSQL 책 데이터와의 동기화 + 백업 + 서버 메모리 나누기가 늘어납니다. 이 프로젝트는 「요청 전에는 새 인프라를 넣지 않는다」는 규칙이 있어 plan에서 따로 정해야 합니다.

## 3. 먼저 거르는 단계의 재현율 (잰 값, 81,078권)

### 3-1. 방법

- 책: 운영과 같은 `book-vectors.bin`(81,078권, int8 + scale).
- 질문: HNSW 보고서의 질문 222개를 실제 인코더로 만든 `queries.f32`(분명한 책 질문 57개 + 짧고 모호한 말).
- 정답: 서버 점수 `(int8 · q) × scale`의 상위 k(k = 60, 120; 서버는 120을 묻고 60을 씀).
- 재현율 = 정답 상위 k 중 거른 N권 안에 든 비율, 질문 222개 평균(p10, 최저도 같이).
- 스크립트: `scripts/aisearch/hnsw/cascade_recall.py`. 원본 `chaekcheck-dev\data\aisearch-hnsw\cascade-recall.json`.

| 이름 | 책 쪽 | 질문 쪽 | 책당 |
|---|---|---|---|
| ham (대칭 해밍) | 부호 비트 | 부호 비트 | 128B |

### 3-3. 두 단계 깔때기 (A의 1·2단계), 평균 / p10 / 최저

| 깔때기 | 상위 60 | 상위 120 |
|---|---|---|
| 해밍 1만 → 비대칭 1,000 | 0.992 / 0.967 / 0.850 | 0.974 / 0.917 / 0.733 |
| 해밍 1만 → 비대칭 2,000 | 0.998 / 1.000 / 0.917 | **0.992** / 0.968 / 0.817 |
| 해밍 2만 → 비대칭 2,000 | 0.998 / 1.000 / 0.933 | 0.993 / 0.975 / 0.833 |

읽는 법:
- 같은 128바이트라도 **비대칭이 해밍보다 훨씬 정확합니다**(N 1,000에서 0.974 대 0.895). 질문 쪽 숫자를 버리지 않기 때문입니다. C(pgvector `bit_hamming_ops`)는 이 비대칭을 쓸 수 없습니다.
- 평균 벡터를 빼고 부호를 잡으면(asym_c) 조금 더 좋아집니다(특히 최저값). KURE 벡터의 각 차원이 0을 중심으로 고르게 퍼져 있지 않아서로 보입니다 [추정].
- **int4는 거의 손실이 없습니다**(N 500에서 0.999). 메모리는 binary의 4배(100만 권 512MB)라, RAM 여유가 있으면 「int4 하나로 거르고 int8로 다시 매기기」도 간단한 길입니다.
- HNSW(81k, k 120, ef_search 200)의 0.869보다 A의 깔때기(0.992)가 높습니다. 다만 아래 5절의 「책이 늘 때」는 따로 재야 합니다.
- 최저값(0.73~0.83)은 「음...」「고양이」 같은 짧고 모호한 질문입니다. HNSW 보고서와 같은 경향으로, 점수가 고르게 퍼진 질문일수록 거친 단계에서 많이 놓칩니다.

## 4. A와 HNSW는 둘 다 「여러 층」인데 메모리가 왜 이렇게 다른가

### 4-1. 차이의 대부분은 색인 안 벡터의 정밀도

RAM에 있어야 하는 것, 100만 권:

| | 색인 안 벡터 | 이웃 연결 | 책당 | 100만 권 |
|---|---|---|---|---|
| A | binary 128B | 없음 | 128B | 128MB |
| B | halfvec 2,048B | 약 200B + 페이지 여유 | 약 2,730B (잰 값 211MiB ÷ 81,078) | 약 2.7GB |
| C | binary 128B | 약 200B + 여유 | 약 0.3~0.5KB [추정] | 약 0.3~0.5GB [추정] |

- B가 A의 약 21배인데, 그중 16배가 「숫자 하나에 16비트냐 1비트냐」(2KB 대 128B)입니다.
- pgvector HNSW는 이웃으로 옮겨 갈 때마다 그 책과의 거리를 바로 계산해야 해서, 색인 안에 벡터를 통째로 넣습니다. 그래서 HNSW라서가 아니라 **halfvec를 넣은 HNSW라서** 큽니다.
- C에 남는 A와의 차이(이웃 연결, 책당 수백 바이트)가 「그래프를 쓰는 값」입니다.

### 4-2. 「층」의 뜻이 다름

- **A의 층 = 정밀도 층.** 모든 책이 1층을 지나고, 층이 올라갈수록 같은 책을 더 정밀한 값으로 다시 봅니다. 거친 층(binary)만 RAM에 두고, 정밀한 층(int8)은 소수만 읽으니 디스크에 둬도 됩니다.
- **HNSW의 층 = 길 찾기 층.** 위층은 일부 책만 있는 고속도로, 아래층은 모든 책이 있는 골목입니다. 정밀도는 모든 층이 같습니다.
- 비유: A는 「전교생 명단에서 키를 대충 보고 2,000명을 추린 뒤 그 사람들만 정밀하게 재기」, HNSW는 「친구의 친구를 따라가며 키 큰 사람 찾아가기」입니다.

### 4-3. RAM이 꼭 필요한지가 다름

- A의 1단계는 binary 배열을 처음부터 끝까지 **순서대로** 읽습니다. 128MB는 RAM에 두기 쉽고, 디스크는 마지막 2,000줄만 읽습니다.
- HNSW는 이웃을 따라 **무작위로 점프**하고, 다음에 어디로 갈지는 방금 계산한 거리로 정해집니다. 색인이 디스크에 있으면 점프마다 디스크 읽기가 됩니다. HNSW 보고서 3-6절에서 컨테이너 메모리를 색인보다 작게 하자 12ms → 202~224ms가 된 것이 이 경우입니다.

- 한 줄: **A는 메모리를 아끼고 시간을 쓰고, HNSW는 메모리를 써서 시간을 아낍니다.** C·D는 둘을 섞은 형태라 100만 권 이상에서 후보가 됩니다.

## 6. 해밍 거리와 XOR

- binary 벡터의 비트 하나는 「그 차원의 값이 +인가 −인가」입니다.
- XOR은 두 비트가 같으면 0, 다르면 1입니다. 그래서 `질문 XOR 책`의 1의 개수 = 부호가 다른 차원 수 = **해밍 거리**(0~1,024, 작을수록 가까움).

```
질문  1 0 1 1 0 0 1 0
책    1 1 1 0 0 0 1 1
XOR   0 1 0 1 0 0 0 1   → 1이 3개 → 해밍 거리 3
```

- 부호가 다른 차원의 비율은 두 벡터 사이 각도와 거의 비례해서, 해밍 거리가 코사인 유사도를 거칠게 대신합니다.
- 빠른 이유: CPU는 64비트를 XOR 한 번에, 1의 개수를 popcount 명령 하나(`Long.bitCount`)로 셉니다. 1,024비트 비교 = `XOR + bitCount` 16번. int8 내적은 곱셈·덧셈 1,024번입니다.

```java
int dist = 0;
for (int i = 0; i < 16; i++) dist += Long.bitCount(q[i] ^ book[i]);
```

- 비대칭 binary(2단계)는 XOR을 쓰지 않습니다. 질문 숫자에 책 비트에 맞춰 +1 또는 −1을 곱해 더합니다(`Σ q[i] × (bit ? +1 : −1)`). 해밍보다 조금 느리고 더 정확합니다.

## 8. 서버 코드 (2026-10-30, 배포 전)

브랜치 `claude/aisearch-vector-funnel`(main 38a34933에서).

| 파일 | 하는 일 |
|---|---|
