## 0. 이름표: 이 문서에 나오는 방식·모델 이름

**2-2절 (첫 질문, 전체 흐름)** — 자세한 정의는 [1차 호출 보고서 0절](2026-10-25-first-call-models.md)

|---|---|---|---|---|
| H | Haiku 1차(그때 운영 지시문, 앞 대화 함께) | Haiku 검색어, 지금 질문만의 벡터, 칸 없음 | 막음(카드 0장) | 늘, 앞 책 제목만 |

| M8 | 같음 | M4와 같음 | 막지 않음 | 제목만, 단 새 주제 규칙이 켜지면 보내지 않음 |

M4가 v1.16.0 운영의 이어 묻기 방식(설정 `FOLLOW_UP=rule`)이 됐습니다. M2·M3·M5는 재지 않았습니다(3-2절).

**이어 묻기 묶는 법 (3-4 · 3-5절, 설정 `CHAEKCHECK_AISEARCH_FOLLOW_UP`)**

| 값 | 무엇 | 운영 |
|---|---|---|
| rule | M4의 새 주제 규칙 | v1.16.0. 지금은 `follow-up-model.bin`이 없을 때만 |
| strict | rule과 같되, 「앞 질문 + 지금 질문」 이은 글의 MLP 큰 칸도 앞 질문 큰 칸과 안 겹칠 때만 새 주제(`MlFirstCall`) | 내지 않음 |
| **relation** | 관계 분류기(7가지, 3-4 B)가 정한 관계에 따라 이어받을 것을 정함 | **v1.16.1부터 지금까지** |

**채점 지표** (2-2 · 3-2 · 3-4 · 3-5 · 3-6절): Sonnet이 (질문 또는 대화, 책)마다 0~3점. **맞음** = 보인 카드 중 2~3점 비율, **아주 맞음** = 3점 비율, **틀린 카드** = 질문 하나에 보인 0~1점 카드 수, **카드 0장** = 카드 없는 답 수. 카드는 2차가 fit 2 이상 준 책, 최대 8장(운영과 같음). 이어 묻는 질문은 대화 전체(첫 질문, 보인 책, 지금 질문)를 보고 매김(`fu-JUDGE_RULES.md`, `fu2-JUDGE_RULES.md`, `c3-JUDGE_RULES.md`). 자세한 뜻은 [모음 「숫자 읽는 법」](../4-portfolio.md).

## 1. 무엇을 바꾸려는가

```
바꾸기 전(v1.15.x):       질문 ─▶ [1차 Haiku] 길 나누기 + 검색어 ─▶ 후보 30권(낱말 + KURE 벡터) ─▶ [2차 Haiku] 카드 고르기
바꾼 것(v1.16.0~ 운영):   질문 ─▶ [KURE 벡터 + MLP] 길 나누기 + 칸     ─▶ 후보 30권(질문 낱말 + 벡터 + 칸) ─▶ [2차 Haiku] 그대로
```

- 1차 Haiku가 하는 일: ① 길 나누기(책 찾기 아님 → 막음 / 제목·저자만 → 「직접 찾기」 버튼 / 앞에서 보인 책을 가리킴 → 그 책들 안에서 다시 고름), ② 검색어 만들기.
- 바꾼 뒤 후보 만들기: 낱말 후보 = 질문 낱말(M 방식)로 `search_book`에 `LIKE`, 벡터 후보 = 질문 벡터와 책 벡터의 내적 순, 둘을 RRF(점수 = Σ 1/(60 + 순위))로 줄 세우고 질문 칸과 책 프로필 칸이 같은 칸 하나마다 +0.004, 빼 달라는 칸의 책은 맨 뒤 → 30권. 계산 자세히는 [1-how-it-works 4-7~4-9절](../1-how-it-works.md).
- 바꾸면: 1차 호출 1~2.4초와 검색당 비용 약 15%(설정 단가로 낸 추정)가 없어지고(바꾼 뒤 잰 값은 3-5 ①: 비용 −8% $0.00152 → $0.00140, 중앙값 8.6 → 8.1초, 느린 10% 11.4 → 9.7초), API 장애 지점이 하나 줄어듦. KURE 질문 벡터는 검색에 이미 만들고 있어서 MLP 계산(1ms 안쪽)만 더해짐.

## 2. 결정 목록

숫자는 모두 Sonnet이 만든 정답 기준. 흔들림(같은 것을 다시 재면 달라지는 폭): 시험 600개 ±3%p, 400개 ±2.5%p, 전체 흐름 57개 ±3%p 쯤. 이 안의 차이는 「같다」로 봅니다.

## 3. 진행 중 (2026-10-26 그때 이름. 모두 끝나 운영에 들어갔거나 뺐음)

### 3-1. 길 나누기 학습 질문을 얼마나 늘릴까 (같은 400개)

사용자 기준: **선형으로 오르는 동안은 더 학습**, 오름이 흔들림 안으로 줄면 멈춤. 4갈래 v2를 길 나누기 학습 질문 수만 바꿔 다시 학습: 유형마다 같은 수(100 → 200 → … → 600)로, 표의 수는 네 유형 합(400 → 800 → 1,200 → 1,600 → 2,000 → 2,400개). 작은 수는 큰 수에 포함되게 같은 순서로 뽑음. 칸 학습 질문 6,298개는 늘 함께. MLP는 시작값 3개로 돌린 평균, LR은 한 번. tau는 학습량마다 기준값용 질문으로 다시 고름. 결과 [`route-steps.json`](../../reports/ai-search-eval/first-call/route-steps.json), 도구 `route_steps.py`.

|---|---|---|---|
| 400 | 90.2% | 88.2% | 6.0 |

### 3-2. 이어 묻는 질문 (2번째 질문)

**무엇을 왜**: 1차 호출 보고서 5-5·5-6은 앞 대화 없는 첫 질문만 쟀음. 이어 묻는 질문도 1차를 ML로 바꿔도 되는지, 2차에 앞 대화를 어떻게 보낼지 잼.

**질문**: 첫 질문 57개(그때 운영이 보인 카드 8장씩)마다 Sonnet이 이어 묻는 질문을 다섯 종류로 하나씩 씀 = **285개**(`fu-RULES.md`).

| 종류 | 예 | 1차가 할 일 |
|---|---|---|
| ① refers: 앞 책 안에서 고르기 | 「이 중에 소설만」, 「3번은 어려워?」 | 「앞 책 가리킴」 판단만 |
| ② modify: 조건만 바꾸기 | 「더 쉬운 걸로」, 「이번엔 청소년용으로」 | 앞 주제를 이어받아 새로 찾기 |
| ③ shift: 주제를 좁히거나 옆으로, 더 보기 | 「식단 말고 운동 쪽은?」, 「다른 것도 더」 | 앞 주제 일부를 이어받기 |
| ④ new: 전혀 다른 주제 | 「이번엔 추리소설 추천해줘」 | 앞 주제를 **버려야** 함 |
| ⑤ chat: 책 찾기가 아닌 말 | 「고마워 잘 읽을게」 | 카드를 보이지 않아야 함 |

이 다섯 종류 이름(refers·modify·shift·new·chat)은 시험 질문의 종류입니다. 3-4절 관계 분류기의 관계 7가지(refers·ask_one·continue·shift·feedback·new·none)와 비슷하지만 같은 목록이 아닙니다(modify ≈ continue, chat ≈ none).

**비교하는 1차 방식**: 0절 「이어 묻는 질문 방식」 표(H · M4 · M6 · M7 · M8). 간단히:

| 방식 | 1차 | 앞 대화 처리 |
|---|---|---|
| H | Haiku (그때 운영 v1.15.x, 앞 대화 함께) | Haiku가 알아서 |
| M4 | MLP + 새 주제 규칙 | 앞 질문의 칸·낱말·벡터를 이어받고 지금 질문의 칸으로 덮어씀. 지금 질문만으로 큰 분야가 정해지고 앞과 다르면 앞 질문을 버림. 「책 찾기 아님」은 막음 |
| M6 | M4 + 막지 않기 + 자세한 앞 대화 | 「책 찾기 아님」이어도 검색해서 2차에게. 2차에 앞에서 보인 책을 번호·저자·한 줄 소개와 함께(그때 운영은 제목만) |
| M7 | M6 + 필요할 때만 | 새 주제 규칙이 켜지면 2차에 앞 대화를 아예 보내지 않음 |
| M8 | M4 + 막지 않기 + 필요할 때만 (제목만) | M7과 같되 앞 대화는 제목만 |

(처음 짠 M2·M3·M5는 2차 호출 비용 때문에 뺌: 한 번에 약 2만 토큰이라 285개 × 6방식이면 에이전트 약 250개. 사용자 결정으로 **첫 질문 20개 × 5종류 = 100개, 방식 5개**로 줄임.)

**채점**: Sonnet이 대화 전체(첫 질문, 보인 책 8권, 지금 질문)를 보고 카드마다 0~3점, 카드 1,014장 모두(`fu-JUDGE_RULES.md`). chat은 「카드 0장」이 정답. **종류마다 20개뿐이라 흔들림이 큼(±10%p 안팎)**. 한 번씩. 카드 목록 [`followup-cards.json`](../../reports/ai-search-eval/first-call/followup-cards.json), 점수 `data/aisearch-eval-2026-10-25/fu/judged.json`, 도구 `fu_facets.py` → `fu_cands.py` → 2차 → `fu_judge.py score`.

### 3-3. 5갈래: 「책첵 질문」 더하기 (시험 600개, 2026-10-26)

책첵 자체(무료인지, 가입, 정보 출처)나 전자도서관 이용(다른 지역 가입, 대출·연장은 어디서)을 묻는 질문을 따로 알아보는 갈래. 답은 소개 탭·첫 화면 정보로 Haiku가 함(사용자 결정: ML 전환 때 함께 만듦).

- 모델: 4갈래 v2와 같은 모양에 갈래 하나를 더한 5갈래(1024 → 512 → 5, `route5.py`).
- 학습: 갈래마다 같은 수(표의 200 · 400 · 600) + 칸 학습 질문 6,298개. 책첵 질문 갈래 = Sonnet이 쓴 책첵 질문 600개 + 기존 「책 찾기 아님」 중 Sonnet이 책첵 질문으로 다시 나눈 22개. 「책첵에서 추리소설 찾아줘」처럼 헷갈리는 책 찾기 300개는 「보통 질문」으로, 갈래 수의 절반만큼.
- 시험 600개: 기존 400개(다시 나눈 11개 포함) + 책첵 질문 100 + 헷갈리는 책 찾기 100. MLP는 시작값 3개 평균. 결과 [`route5-scores.json`](../../reports/ai-search-eval/first-call/route5-scores.json).

|---|---|---|---|---|---|---|---|---|
| 200 | 92.7% | 86.1% | 92.7% | 96.0% | 92.2% | 94.2% | 95.7% | 6.7 |
| 400 | 94.5% | 89.9% | 94.0% | 98.0% | 93.7% | 95.5% | 98.7% | 5.7 |
| 600 | **94.6%** | 91.8% | 92.7% | 100% | 92.5% | 95.3% | 98.7% | 2.3 |

- 「막음」= 책 찾는 질문을 「책 찾기 아님」이나 「책첵 질문」으로 보내 검색이 안 되는 수(600개 중, 시작값 3개 평균).
- **결정: 갈래당 600개에서 멈춤** — 400 → 600에서 +0.1%p로 평평. 막음 5.7 → 2.3개로 줄어 4갈래(1.7)와 비슷. 이 600개 판이 **v1.16.0 운영 파일**(tau 0.30, 백업 `v3-5way-2026-10-26`).
- 막힌 것(시작값 0): 「그 많던 싱아는 누가 다 먹었을까」, 「불편한 편의점」(제목만), 「경제」(한 낱말) — 모두 「책 찾기 아님」으로 감. **책 찾기를 「책첵 질문」으로 막은 것은 0개.**
- 「책첵 질문」을 놓친 8개는 모두 「책 찾기 아님」으로 감(「내 대출 현황 보여줘」, 「반납 연기 신청 가능?」, 「넌 뭘 할 수 있어?」 등). 둘 다 검색을 하지 않으므로 손해는 답 문구가 「찾지 못했어요」가 되는 것뿐. 대부분 사이트 정보로도 정확히 답하기 어려운 개인 대출 문의.

### 3-4. 운영에서 나온 문제 고치기: 짧은 장르 질문, 이어 묻는 질문 관계 (2026-10-26)

v1.16.0을 쓰다가 사용자가 두 가지를 찾음: ① 「판타지인데」 → 「좀 슬프고 서정적인거」처럼 이어 물으면 앞 질문이 이어지지 않음, ② 「고마워」에 「맞는 책을 찾지 못했어요」가 나옴. 원인과 고친 것:

- ①의 원인은 3-2의 **새 주제 규칙**(M4, 설정 `rule`): 지금 질문만으로 큰 분야가 정해지고 앞과 다르면 앞 질문을 버림. 「서정적인거」는 혼자서 「시」로 정해져 「소설」인 앞 질문을 버림. 이어 묻는 질문 171개에서 이 규칙이 **47번 잘못 켜짐**.
- 짧은 장르 질문(「판타지」, 「추리소설 추천」)은 길 나누기에서 「제목만」·「책 찾기 아님」으로 많이 샘: 짧은 질문 시험에서 운영 모델(v1.16.0 5갈래) 74%.

소제목 A·B·C는 이 절 안의 순서입니다(사용자 「A·B를 다 잰 다음에 한 번에 바꾸자」의 A·B). 「라우터 B」(모델 이름)와 다릅니다.

**A. 길 나누기에 짧은 장르 질문 300개 더하기 (라우터 B)**

라우터 B = 3-3절 5갈래(갈래당 600)와 같은 학습에 Sonnet이 쓴 짧은 장르·분위기 질문 300개를 「보통 질문」으로 더해 다시 학습한 5갈래 MLP(`route5b.py`). 짧은 질문 시험 = 따로 쓴 100개(`short-7`).

**B. 이어 묻는 질문의 관계를 따로 분류 (관계 분류기)**

앞 질문과 지금 질문의 관계를 7가지로 나누는 MLP 하나: refers(앞 책 안에서) · ask_one(앞 책 한 권을 물음) · continue(조건 더하기) · shift(주제 옮기기) · feedback(앞 결과에 대한 반응 + 다시 찾기) · new(새 주제) · none(책 찾기 아님). 입력은 지금 질문, 앞 질문, 둘을 이은 글(「앞 질문 + " " + 지금 질문」)의 KURE 벡터와 지금·앞 벡터의 칸마다 곱(합쳐 4,096) → 512 → 7. 학습은 Sonnet이 쓴 질문 쌍 관계마다 400개(new는 399), 시험은 따로 쓴 700개(관계마다 100). MLP는 시작값 3개 평균. 결과 `data/aisearch-eval-2026-10-25/rel/rel-steps.json`, 도구 `rel_train.py`.

### 3-5. 빠진 측정 세 가지: 속도·비용, 반복 흔들림, 두 번째 채점자 (2026-10-26)

사용자 "빠진 측정 세 가지 채워서 문서에 넣어 줘". 모두 로컬 서버(v1.16.1 코드, 같은 PC, 실제 Haiku 5.5)에서 잼.

**① 1차를 Haiku → ML로 바꾼 속도와 비용 (평가 질문 57개, 첫 질문만, 같은 코드·같은 PC에서 설정만 바꿔 연달아)**

|---|---|---|
| 답이 끝날 때까지 (중앙값 / 평균 / 느린 10%) | 8.6 / 8.4 / 11.4초 | 8.1 / 7.5 / **9.7초** |
| 입력 / 출력 토큰 (1차 + 2차 합) | 7,621 / 1,515 | 6,365 / 1,522 |

**② 이어 묻는 질문 시험의 흔들림 (3-4의 대화 80개, rule과 relation을 3번씩)**

첫 질문 카드는 같은 것(`turn1.json`)을 쓰고 이어 묻는 질문만 다시 물음. 새로 나온 카드만 Sonnet이 같은 채점표로 채점(같은 대화·같은 책은 앞 점수를 다시 씀). 1번 = 3-4 표의 값, 2·3번 = `turn2-<방식>-r2`·`-r3`.

| 방식 | 1번 | 2번 | 3번 | 평균 (폭) | continue 평균 (폭) | 카드 없는 답 (70문) |
|---|---|---|---|---|---|---|
| rule | 72.2% | 74.2% | 76.4% | 74.3% (72.2~76.4) | 67.4% (64.1~70.9) | 14 · 14 · 12 |
| relation | 75.4% | 76.5% | 76.5% | **76.2%** (75.4~76.5) | **76.2%** (73.0~79.3) | **9 · 8 · 7** |

- 「70문」= ask_one 10과 none 10을 뺀 refers 10 · continue 20 · shift 15 · feedback 10 · new 15.
- **전체 맞음 차이(+1.9%p)는 rule 자체의 흔들림(4.2%p) 안**이라, 3-4의 「72.2 → 75.4%」는 한 번씩 돌린 값이라 차이를 크게 보였음. 전체로는 「조금 낫거나 비슷함」이 맞는 말.
- 흔들림을 넘는 차이는 **continue(조건 더하기)**: 3번 모두 relation이 위(가장 낮은 73.0 > rule 가장 높은 70.9), 그리고 **카드 없는 답** 12~14 → 7~9. 사용자가 찾은 「판타지인데 → 서정적인거」가 이 유형.
- refers(앞 책 안에서)는 rule 52~67%, relation 43~46%로 relation이 낮은 편. 관계 판단은 10/10이 맞아 2차 Haiku가 고르는 책 수의 흔들림으로 봄 [추론].
- 결정 24(relation 넣음)는 그대로: 사용자 문제였던 continue와 빈 답이 흔들림을 넘게 나아짐.

**③ 두 번째 채점자 (Sonnet 점수를 Opus로 다시)**

사람이 직접 보는 확인 대신, 3-4·3-5의 카드 중 Sonnet 점수 0·1·2·3점마다 25장(100장)을 Opus 5.5가 같은 채점표로 따로 채점. 사람 확인이 아님. 데이터 `fu2/xj/`, 도구 `fu2_xjudge.py score`.

| | 값 |
|---|---|
| 점수가 같음 | 69% |
| 1점 안 차이 | 99% |
| 맞음(2~3)/틀림(0~1)이 같음 | **88%** (κ ≈ 0.76, 점수마다 같은 수로 뽑아 우연 일치 50%) |

- 다른 것은 대부분 Opus가 한 칸 후함: Sonnet 1 → Opus 2가 7장, 2 → 3이 10장. 반대(2 → 1)는 4장. Sonnet 점수는 엄한 쪽이라 「맞음 %」는 낮게 나올 수는 있어도 부풀려지지는 않음 [추론].
