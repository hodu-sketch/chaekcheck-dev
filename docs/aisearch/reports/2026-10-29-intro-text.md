# 책 소개글을 검색에 어떻게 넣나: 벡터 글, 조각, 낱말 검색(BM25), Haiku가 읽는 글 (2026-10-29)

사용자 요청(2026-10-29) 「임베딩 소개 텍스트 압축 방법 비교 실험」을 따라 잰 기록입니다. 다음 요청도 함께 다룹니다.

- 조각, 조각 + 맥락(Anthropic Contextual Retrieval), 토큰 길이 512 이야기를 확인할 것
- 「전문적이고 지엽적인 질문에 답을 못한다」를 고칠 것
- 요약 벡터와 맥락 조각 벡터의 두 층으로 나눌 것
- 낱말 검색에 넣는 글과 Haiku가 읽는 글을 충분하게 할 것
- BM25, DB 확장(pg_search)을 볼 것
- 다양한 꼴의 검색어로 시험할 것

모든 숫자는 1,000권 표본에서 **잰 값**입니다. 7만 7천 권이나 운영에 맞춘 값은 [추정]을 붙였습니다. 운영 코드는 아무것도 바꾸지 않았습니다.

## 0. 결론 먼저

| 부분 | 지금 (v1.21.x) | 추천 | 근거 (10위 안, 정답 책이 정해진 검색어 800개) |
|---|---|---|---|
| 낱말 검색 | `LIKE`, 맞은 낱말 **개수**, 글 = 제목 + 저자 + 「찾기용 한 줄」(약 100자) | **pg_search 한국어 BM25**(Lindera KoDic), 글 = 제목 + 저자 + 한 줄 + **소개 전문** | 낱말만 썼을 때 전문 용어 58 → 97%, 뒷부분 내용 37 → 93% |
| 책 벡터 글 | 「제목 · 저자 · 출판사 · 연도」 + 소개 **앞 300자** | 같은 머리 + **Haiku 요약**(200~250자). 책당 벡터 1개, 메모리 그대로 | 벡터만 썼을 때 뒷부분 59 → 91%, 전문 79 → 89% |
| Haiku가 읽는 글 | 「한 줄」 | **요약 + 질문 낱말이 나온 소개 토막**(약 160자) | 정답이 후보에 있을 때 고른 비율: 전문 64 → 84%, 오타 64 → 86% |

- 셋을 합친 후보(요약 벡터 + BM25)는 지금 운영 후보보다 낫습니다.
  - 정답 책이 Haiku가 보는 30권 안에 드는 비율이 검색어 8종 모두 **95~100%**입니다(지금 80~98%).
  - 1위 비율은 24~69% → 67~94%입니다.
  - 검색어 800개를 하나씩 짝지어 비교하면, 30위 안에 새로 든 것 86개, 빠진 것 4개입니다.
  - MRR 차이 +0.276, 95% 구간 [0.247, 0.304]입니다(5-1).
- **두 층(요약 + 조각 벡터)** 은 지엽적인 질문의 1위 비율을 더 올립니다. 전문 용어 1위가 79 → 86~89%입니다(95% 구간이 0보다 큼).
  - 하지만 30위 안 비율은 같습니다(BM25가 이미 데려옴).
  - 책당 벡터가 3~9.5배 늘어서 지금 서버(힙 640MB)에는 부담이 큽니다 [추정]. 그래서 **나중 단계**로 둡니다(6-3).
- **맥락(Contextual Retrieval)** 은 조각만 쓸 때보다 1위를 올립니다. 그러나 두 층 + BM25 위에서는 맥락 없는 조각과 거의 같습니다(전문 용어 1위 89 대 87%). 7만 7천 권이면 Haiku 호출이 수십만 번이라 **넣지 않는 쪽**이 맞습니다.
- **토큰 512가 최적이라는 말은 이 데이터에서 맞지 않았습니다.** KURE-v1은 8,192토큰까지 받습니다. 벡터 하나에 통째로 넣을 때 128 → 1024까지 계속 좋아졌습니다(뒷부분 53 → 90%). 그래도 요약이나 조각에는 못 미쳤습니다.
- **조심할 것**: 사용자 질문형 57개(정답 책이 없는 주제 질문)를 Haiku로 채점하면 **벡터만이 BM25를 섞은 것보다 조금 낫습니다**(4-6).
  - 일반 주제 질문에서는 BM25가 흔한 낱말로 잡음 책을 섞습니다.
  - 그래도 추천 구성은 지금 운영보다 좋습니다(상위 10권 중 맞는 책 0.204 → 0.258).

## 1. 지금 운영이 하는 일 (코드와 문서에서 확인)

- 낱말 검색: `catalog.book_search.search_text` = `tidy(제목) + tidy(저자) + tidy(한 줄)`을 `LIKE`로 찾고, 맞은 질문 낱말 수로 정렬합니다. 상위 50권입니다([1-how-it-works 4-7절](../1-how-it-works.md)). 질문 낱말은 `QuestionWords.of`가 뽑습니다(빈칸으로 나누고 → 끝말 떼기 → 요청 낱말 빼기 → 최대 8개).
- 벡터: KURE-v1 책 벡터는 「제목 · 저자 · 출판사 · 연도」 + 소개 앞 300자로 만듭니다(`book-vectors.bin`, 81,078권). 질문 벡터와 가까운 순으로 상위 60권입니다.
- 합치기: RRF k=60 → 30권을 Haiku에게 보냅니다(4-9절).
- Haiku가 읽는 글: 후보마다 「제목 / 저자 / 출간 / 한 줄」입니다(4-10·4-11절). **낱말 검색과 Haiku가 같은 「한 줄」을 씁니다.**
- 길이(이번 표본 1,000권): 한 줄 중간값 **93자**(한 줄이 있는 책 665권), 소개 전문 중간값 816자(평균 1,402자), 소개 전문 토큰 중간값 **425**(p90 1,760, 최대 3,356). 300자를 넘는 소개가 84.3%라, 지금 벡터와 한 줄에는 소개 뒷부분이 들어가지 않습니다.

## 2. 실험 설계

### 2-1. 표본과 검색어

- 책: 100k 소개 파일에서 소개가 50자 이상인 76,974권 중 1,000권을 뽑았습니다(SEED 20261029). 모든 방식이 이 1,000권 안에서 찾습니다.
- 정답 책이 정해진 검색어 800개는 Sonnet(`claude-sonnet-5-5`)이 썼습니다. 그 책 소개를 보고 사람이 칠 만한 검색어를 만들게 했습니다.

| 종류 | 개수 | 만든 법 | 예 |
|---|---|---|---|
| 전체 | 100 | 소개 전체 내용으로 | |
| 뒷부분 | 100 | 소개 300자 뒤에만 나오는 내용으로(소개 700자 이상 책) | |
| 전문 용어 | 100 | 소개에 나오는 개념·인물·지명·용어 하나 | 「하이젠베르크 불확정성 원리 쉽게 설명해주는 책 추천해줘」 |
| 오타 | 100 | 전문 용어 검색어의 핵심 낱말을 흔히 틀리는 대로 | 「하이젠베르그 …」 |
| 다른 이름 | 100 | 영어 원어, 줄임말, 다른 표기 | 「Heisenberg 불확정성 원리 …」 |
| 낱말만 | 100 | 핵심 낱말 1~3개 | 「불확정성 원리」 |
| 풀어 말하기 | 100 | 용어 없이 내용 설명 | 「입자의 위치와 운동량을 동시에 정확히 알 수 없다는 양자역학 원리…」 |
| 독자 조건 | 100 | 「입문자」「초등학생」 같은 조건 더함 | 「과학 입문자도 이해할 수 있게 …」 |

- 정답 책이 없는 주제 질문 57개: 기존 평가 질문(`scripts/aisearch/eval/eval_questions.json`)입니다. 방식마다 상위 10권을 모아 Haiku가 책마다 0~3점을 매겼습니다(4-6).

### 2-2. 지표

- **10위 안 / 30위 안 / 1위**: 정답 책이 그 순위 안에 든 검색어 비율입니다. Haiku는 30권을 보니 30위 안이 「후보에 들어왔나」입니다.
- **MRR**: 1 / 정답 순위의 평균입니다. 짝 비교는 같은 검색어끼리 MRR 차이를 2,000번 다시 뽑아(부트스트랩) 95% 구간을 냅니다.
- **Haiku 고르기**: 정답 책을 지금 후보 30권(`base300+kw_line`) 안에 반드시 넣고(없으면 무작위 자리), 책마다 읽는 글만 바꿔 Haiku에게 0~8권을 고르게 합니다. 「정답을 골랐나 / 첫 번째로 골랐나」를 봅니다.

### 2-3. 조심할 점

- 검색어를 LLM(Sonnet)이 썼습니다. 그래서 LLM이 쓴 글(요약, 맥락)이나 소개 낱말을 그대로 쓰는 BM25가 유리할 수 있습니다. 같은 회사 모델이라도 Haiku가 아닌 Sonnet으로 써서 줄이려 했고, 사람 질문형 57개 채점(4-6)으로 확인했습니다.
- 이 1,000권 중 335권은 「한 줄」이 없습니다(`search-lines.tsv`에 없음). 그래서 「지금 운영」 낱말 검색은 이 책들을 제목·저자로만 찾습니다. 운영 DB의 한 줄 채움 비율은 이 실험에서 재지 않았습니다.
- 「지금 운영」 줄에는 ML 1차의 칸 보너스·빼기(프로필)가 없습니다. 순서가 운영보다 조금 나쁠 수 있지만, 30위 안 비율은 대부분 후보 목록에 들어왔느냐로 정해집니다.
- 1,000권에서 BM25의 「드문 낱말」 정도(IDF)를 계산했습니다. 7만 7천 권에서는 값이 달라집니다.

## 3. 시험한 방식

### 3-1. 벡터에 넣는 글 (모두 앞에 「제목 · 저자 · 출판사 · 연도」)

| 이름 | 글 | 책당 벡터 |
|---|---|---|
| base300 (지금) | 소개 앞 300자. 운영 벡터와 코사인 평균 0.99989 (같은 글 확인) | 1 |
| c500 | 소개 앞 500자 | 1 |
| prefix | Haiku가 소개 전체를 읽고 쓴 2~3문장(80~150자) + 앞 300자 | 1 |
| summary | Haiku 요약 200~250자(핵심 용어·인물 이름 남기기) | 1 |
| tok128 ~ tok1024 | 소개 통째(최대 6,000자)를 넣고 모델이 앞 N토큰만 읽음 | 1 |
| chunk128 / 256 / 512 | 소개를 N토큰 이하 **문장 단위** 조각으로. 책 점수 = 가장 가까운 조각 | 8.5 / 3.7 / 2.0 |
| ctx128 / 256 / 512 | 조각마다 Haiku가 「소개 전문 + 이 조각」을 읽고 쓴 1~2문장 맥락을 앞에 붙임 | 같음 |
| two-max-X | 요약 점수와 조각 점수 중 큰 것 (사용자 제안 두 층) | 1 + 조각 |
| two-rrf-X | 요약 순위와 조각 순위를 RRF | 1 + 조각 |

조각 자르기(`pack`)는 이렇게 합니다.
- 문장 끝(`. ! ? 。 …`, 「~다·요·죠·음·함·임」 뒤 빈칸, 줄바꿈)에서 나누고, 문장을 하나씩 담다가 N토큰을 넘으면 끊습니다.
- 한 문장이 N토큰보다 길 때만 낱말 사이에서 자릅니다. 문장 끝이 아닌 조각은 128: 379 / 8,535(4%), 256: 150 / 3,701, 512: 142 / 1,965입니다.
- 맥락 지시문은 Anthropic Contextual Retrieval과 같은 꼴입니다(`<document>` + `<chunk>` → 「이 조각이 글 전체에서 무슨 내용인지」).

### 3-2. 낱말 검색

| 이름 | 점수 | 찾는 글 |
|---|---|---|
| kw_* (지금 방식) | 맞은 낱말 수 | line(지금) / intro(+ 소개 전문) / summary(+ 요약) / terms(+ Haiku 검색 낱말 30~50개) |
| bm25word_*, bm252gram_* | Python으로 계산한 BM25 (k1 1.2, b 0.75). 낱말 단위 / 두 글자 단위 | 같음 |
| **pgko_*** | **PostgreSQL pg_search 0.26.3 BM25, `pdb.lindera(korean)`** | 같음 + introonly(한 줄 없이 제목 + 저자 + 소개) |
| pg2g_* | pg_search BM25, `pdb.ngram(2,2)` | 같음 |

pg_search는 시험용 컨테이너에서만 돌렸습니다.
- 이미지: 운영과 같은 `chaekcheck/postgres-bigm:18` + `postgresql-18-pgvector` + `postgresql-18-pg-search_0.26.3-1PARADEDB-trixie_amd64.deb`
- `shared_preload_libraries=pg_bigm,pg_search`. pg_bigm, pg_search, vector(0.8.7)가 한 DB에서 함께 켜졌습니다.
- Dockerfile: `chaekcheck-dev/data/aisearch-intro-text-2026-10-29/pgsearch-image/`. 컨테이너 `chaekcheck-pgsearch-test`, 포트 5530.
- 표마다 `CREATE INDEX … USING paradedb (id, (body::pdb.lindera(korean)))`를 만들고, `WHERE body ||| '질문 낱말들' ORDER BY pdb.score(id) DESC LIMIT 50`으로 찾았습니다.
- 1,000권 색인 0.1~2.9초, 검색 1번 평균 1.5~4.2ms(내 PC, 잰 값)입니다.

### 3-3. 합치기

`{벡터}+{낱말}` = 낱말 상위 50 + 벡터 상위 60을 RRF(k=60)로 합쳤습니다. 운영과 같은 구조이고, 666가지 순위 목록을 만들었습니다.

### 3-4. Haiku가 읽는 글

| 이름 | 「제목 / 저자 / 출간」 뒤에 붙는 것 |
|---|---|
| line (지금) | 한 줄 |
| intro500 | 소개 앞 500자 |
| summary | Haiku 요약 |
| line_snip | 한 줄 + 「소개 일부: …」(질문 낱말 중 가장 긴 것이 소개에 처음 나온 곳 앞뒤 160자) |
| summary_snip | 요약 + 같은 토막 |

## 10. 주제 질문에서 BM25 몫 줄이기 (2026-10-30)

사용자 요청(2026-10-30): "이것도 병렬로 재 줘". 4-6에서 일반 주제 질문(「우울할 때 읽을 책」처럼 정답 책이 하나가 아닌 질문)은 벡터만이 BM25를 섞은 것보다 나았습니다(0.293~0.302 대 0.270). 검색이 질문 종류를 가를 수 있으면, 주제 질문에서만 BM25 몫을 줄일 수 있습니다.

### 10-1. 방법

- 기준 구성 = 사용자가 고른 것: 두 층(요약 + 조각 512, 책별 최고 점수) 벡터 상위 60 + pg_search 한국어 BM25(제목 + 저자 + 한 줄 + 소개 전문) 상위 50, RRF k 60. 다시 돌려 이전 값과 같음을 확인했습니다(검색어 800개 MRR 0.863, 주제 57개 0.270).
- 「주제 질문」으로 갈린 질문은 BM25 상위 50 대신 0 / 15 / 25권만 섞습니다.
- 가르는 법 세 가지:
  - **score**: BM25 1위 점수(`pdb.score`)가 문턱보다 낮음. 같은 모양의 다른 값으로 1위 ÷ 10위(**ratio**)도 쟀습니다.
  - **idf**: 질문 낱말 가운데 가장 드문 낱말의 IDF(1,000권 기준, 어느 책에도 없는 낱말은 뺌)가 문턱보다 낮음.
  - **route**: 운영 1차 ML(`first-call-model.bin`의 route, int8 KURE 질문 벡터)이 「제목만(title_like)」이 아니면 주제 질문.
- 문턱은 857개 질문에서 그 값의 하위 10~70% 지점으로 훑었습니다.
- 두 세트를 함께 봅니다: 검색어 800개(정답 책 있음)의 MRR·R@30, 주제 질문 57개의 상위 10권 중 2점 이상 비율. 새로 상위 10에 들어온 책 7권(질문 6개)은 4-6과 같은 프롬프트로 Haiku가 채점했습니다(약 $0.01 미만 [추정]).
- 스크립트 `scripts/aisearch/eval/bm25_gate_eval.py`(`scores | route | judge | report`). 원본 `gate-bm25-scores.json`, `gate-route.json`, `gate-judge.jsonl`, `gate-report.json`(같은 데이터 폴더).

- **BM25를 15권이나 25권으로 줄이는 것은 효과가 없었습니다.** 모든 문턱에서 주제 57개가 0.260~0.277로 기준(0.270)과 같거나 낮았습니다. RRF는 순위만 쓰므로 BM25 1~15위가 그대로 상위 10에 섞이기 때문입니다. 효과는 **BM25를 아예 빼야** 납니다(위 표는 모두 뺀 경우).
- **score < 15(BM25 1위 점수가 하위 20%)** 가 두 세트를 함께 지킵니다: 800개 MRR 0.863 → 0.865(R@30 0.991 → 0.985, 800개 중 약 5개가 30위 밖으로), 주제 57개 0.270 → 0.293(벡터만과 같음). 주제 질문 57개 중 39개를 주제로 가르고, 검색어 800개 중에서는 132개만(낱말만 39, 풀어 말하기 29, 다른 이름 23 — BM25가 원래 약한 종류) 갈랐습니다. 전문 용어는 100개 중 11개만 갈렸고 그 MRR은 0.905 → 0.910입니다.
- **idf는 덜 좋습니다**: 드문 낱말이 있어도 주제 질문일 수 있고(「세네카와 쇼펜하우어의 철학」), 1,000권에서는 IDF가 거칠게 나옵니다.
- **route는 가르지 못합니다**: 1차 ML은 검색어 800개 중 725개를 「보통 책 질문」으로 봅니다(전문 용어 100개 중 93개). 1차의 갈래는 「책 질문인가, 제목만인가」를 가르는 것이지 「특정 책인가, 주제인가」를 가르지 않습니다.
- **주제 57개의 차이는 아직 우연과 구분되지 않습니다**: score < 15의 +0.023은 질문별 부트스트랩 95% 구간 [-0.007, +0.056], 좋아진 질문 13 / 나빠진 질문 10입니다. 모두 벡터만으로 바꿔도 같은 구간입니다([-0.011, +0.058]).

### 10-3. 판단과 주의

- 제안: **BM25 1위 점수가 낮은 질문(하위 약 20%)에서는 BM25 목록을 섞지 않음.** 특정 책 찾기는 지키면서(MRR 0.865) 주제 질문은 벡터만 수준(0.293)이 됩니다. 검색 한 번에 이미 나오는 숫자라 비용이 없습니다.
- **문턱 15는 그대로 옮기면 안 됩니다.** BM25 점수는 IDF(책 수와 낱말 분포)에 따라 크기가 바뀝니다. 1,000권의 15는 7만 7천 권에서 다른 값입니다. 운영에 넣을 때는 7만 7천 권 재측정(6-1의 1번)에서 「1위 점수 하위 20%」를 다시 잡고, 같은 두 세트로 확인합니다.
- 주제 질문이 57개뿐이라 차이가 통계적으로 확실하지 않습니다. 넣기 전에 운영 질문 로그에서 주제 질문을 더 모아(예: 200개) 다시 재는 것을 권합니다. 그때까지는 설정으로 켜고 끌 수 있게(문턱 0 = 끔) 둡니다.
- 0.293은 「벡터만」의 값이 상한에 가깝습니다(벡터만 0.293~0.302). 가르기는 BM25가 주제 질문에 넣는 잡음을 없앨 뿐, 그 이상은 아닙니다.

## 11. 원문 없이: 한 번의 호출로 요약 + 검색 낱말, Haiku가 읽는 글, 낱말 BM25에서의 가르기 (2026-10-30)

사용자 결정(2026-10-30): "한 줄 + Haiku 검색 낱말 (원문 불필요)로 가자". 소개 원문은 PC에만 둔다는 사이클 23 결정([확정])을 지키므로, 운영에는 Haiku가 쓴 글만 갑니다. BM25 글 = 제목 + 저자 + 한 줄 + **Haiku 검색 낱말**, 벡터 = 두 층(요약 + 조각 512, 조각은 PC에서 원문으로 만들고 벡터만 올림), Haiku가 읽는 글 = 요약 + 질문과 맞은 검색 낱말. 개발 계획의 0단계로, 같은 1,000권에서 세 가지를 쟀습니다.

### 11-1. 방법

- 스크립트 `scripts/aisearch/eval/terms_onecall_eval.py`(`llm | embed | pgsearch | judge | pick | report`). 원본 `onecall.jsonl`, `vec-summary1.npy`, `onecall-bm25-scores.json`, `onecall-judge.jsonl`·`onecall-judge-pools/`, `onecall-pick.jsonl`, `onecall-pick-stats.json`, `onecall-report.json`(같은 데이터 폴더).

### 11-5. 운영에 주는 뜻

- **요약과 낱말은 Haiku 한 번 호출로 같이 만듭니다.** 따로 부른 것과 성능이 같고(구간이 0을 포함), 호출이 반입니다. 1,000권에 약 $0.48 → 7만 7천 권 약 $37, 배치 약 $18 [추정, 표본 비례].
- **Haiku가 읽는 글은 요약 + 맞은 낱말**(` / 검색 낱말: a, b, c`). 원문 토막보다 낫고 원문이 필요 없습니다. 낱말 전부는 붙이지 않습니다. 맞은 낱말 고르기(두 글자 겹침)는 서버에서 질문 낱말로 바로 할 수 있습니다.
- **BM25 가르기(10절)는 넣지 않습니다**: 낱말 BM25에서는 주제 질문을 해치지 않습니다. 7만 7천 권 재측정(개발 계획 6단계)에서 같은 두 세트로 한 번 더 확인합니다.
- 주의: 주제 57개는 여전히 작은 표본이고, 이 절의 주제 점수는 채점을 채운 값이라 4-6·10절과 바로 비교하면 안 됩니다. B는 400개 표본이고 Haiku 고르기 자체의 흔들림이 있습니다.
