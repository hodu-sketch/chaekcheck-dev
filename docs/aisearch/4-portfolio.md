## 0. 이 문서가 답하는 것 / 답하지 않는 것

- 답하는 것: 책첵 「AI 책 찾기」를 고치며 잰 **모든 전후 비교**를 한 곳에. 주제마다 「문제 → 원인 → 고친 것 → 결과(전 → 후 숫자)」, 재 보고 버린 안, 숫자 읽는 법, 배운 것, 한계.
- 답하지 않는 것:
  - 지금(v1.19.0) 질문 하나가 어느 표·파일을 어떤 계산으로 다루나 → [1-how-it-works.md](1-how-it-works.md)
  - 버전마다 바꾼 것·날짜·커밋·그 뒤 → [2-versions.md](2-versions.md)
  - ML 모델을 어떻게 학습했나 → [3-ml-models.md](3-ml-models.md)
  - 운영 명령·파일·설정 → [../maintenance/6-aisearch.md](../maintenance/6-aisearch.md)
  - 실험 하나의 자세한 방법(질문 목록, 채점 기준, 원본 파일) → 각 줄에 링크한 [reports/](reports/) 보고서
- **같은 질문 묶음끼리만 비교할 수 있습니다.** 절마다 잰 질문 묶음(50개, 57개, 72개, 80문항 …)이 달라 숫자를 이어 붙여 읽으면 안 됩니다.

## 숫자 읽는 법

- 질문 하나에 카드 최대 8장. Sonnet이 질문×책마다 0~3점을 매긴 **같은 채점표**로 모든 안을 셈.
- **맞음%** = 카드 중 2~3점(주제가 맞음). **아주 맞음%** = 3점(주제와 조건 — 대상·쉬움·나라·장르 — 이 다 맞음). **틀린 카드** = 질문 하나에 보이는 0~1점 카드 수.
- **흔들림**: 같은 입력을 두 번 돌리면 아주 맞음 ±1~3%p, 틀린 카드 ±0.2장 → **3%p 이하 차이는 차이로 보지 않음**.
- **드는 것**: 2차 AI에 넣는 글자 수(비용 대용), 서버 메모리·시간, 만드는 데 든 작업.

## 5. 1차 AI 호출을 작은 모델로 — [1차 호출 보고서](reports/2026-10-25-first-call-models.md) · [넣은 것과 뺀 것](reports/2026-10-26-ml-first-call-decisions.md)

v1.15까지 1차 호출(Haiku)은 질문을 읽고 검색어와 칸(분야·작은 칸·장르·대상 등)을 JSON으로 냈습니다(v1.16.0부터는 작은 신경망이 함). 이 중 「정해진 칸에서 고르기」를 LLM 없이 할 수 있는지, Sonnet이 만든 질문 3,000개(학습 2,306 / 시험 600)로 잼. 모델 자체의 설명은 [3-ml-models.md](3-ml-models.md).

### 5-2. 전체 흐름에 넣으면 (질문 57개, 2차 Haiku까지)

비교한 안: **P** = 그때 운영(1차 Haiku가 검색어·핵심어, 칸 없음 → 낱말·벡터 후보 RRF → 2차 Haiku). **M** = 1차 Haiku 없이 낱말은 질문 낱말 그대로, 칸은 MLP가 정해 칸 보너스. **MT** = M + 책 프로필의 주제어(2권 이상에 붙은 약 10,400개를 KURE 벡터로 바꿔 둠) 가운데 질문 벡터와 가장 가까운 것을 낱말에 더함(질문 낱말 최대 4 + 주제어 최대 4, `scripts/aisearch/eval/topics_kw.py`).

M·MT를 두 번 돌린 평균 아주 맞음 **72 / 71.5%**, 틀린 카드 **0.36 / 0.35** — P(72%, 0.37)와 같음. 책 찾는 질문에서는 1차 Haiku 호출(1~2.4초, 비용 약 15%)을 없애도 최종 카드가 나빠지지 않음([5-4절](reports/2026-10-25-first-call-models.md)).

## 6. 운영에서 사용자가 찾은 문제 고치기

사용자가 운영에서 직접 찾은 사례를 그대로 시험으로 만들고, 고친 뒤 같은 시험과 기존 시험(회귀 확인)으로 다시 잼.

| 찾은 것 | 원인 | 고친 것 | 전 → 후 |
|---|---|---|---|
| 「ai agent나… → llm인가 → 위에 언급한 두 개에 관한 책」에 프롬프트 엔지니어링 책 | 「앞 책 가리킴」 후보가 바로 앞 턴 책 2권 + 그 이웃뿐, 앞 질문 둘을 함께 보지 않음 | 그 전 턴들의 책도 후보에 넣음 (v1.16.2), 앞 질문 여럿을 이어 붙여 「앞 질문」으로 씀 (v1.16.3) | v1.16.2로는 그대로, v1.16.3에서 AI 에이전트 책과 LLM 책이 함께 나옴 |
| 시기를 묻지 않았는데 「2026년 기준 최신 책은 찾기 어렵지만」 | 2차 책 목록에 준 「출간: YYYY년」을 늘 씀 | 2차 지시문 `PICK_SYSTEM`에 「연도·올해·최신은 질문이 시기를 물을 때만」 (v1.16.2) | 시기 말을 꺼낸 답 16개 중 1 → 0 |
| 「판타지 → 추리 → 두 개 섞은 느낌」에 카드 1장 | 관계 분류기는 바로 앞 질문 하나만 봄 | 「두 개」·「둘 다」·「섞은」이면 앞 질문 2개를 이어 붙여 「앞 질문」으로 씀 (v1.16.3) | 6장, 판타지와 추리가 섞인 소설 |
| 「…입문서지만 전문적」 → 「수학적인 것도 좀」에 「수식보다 실습 중심」 책 | 2차가 조건과 반대인 책도 주제만 맞으면 넣음 | `PICK_SYSTEM`에 「책 정보가 조건과 반대면 fit 1, 앞 조건도 지키기, 조금만 채우면 그만큼만 말하기」 (v1.16.3) | 3번 모두 반대인 책 0권, 5권씩 |

**3번 이어지는 대화 50개** (Sonnet이 씀, 세 번째 질문의 카드를 Sonnet 채점, [3-6](reports/2026-10-26-ml-first-call-decisions.md))

| | v1.16.2 | v1.16.3 |
|---|---|---|
| 앞 주제 둘 합치기 25개: **카드 0장** | **12개** | **1개** |
| 마지막 질문만 잇기 15개 (「두 권만」·「둘 중에」 같은 헷갈리는 말 포함): 맞음 / 틀린 카드 | 85% / 0.73 | **92% / 0.40** |
| 보인 책 가리키기 10개: 맞음 | 69% | **87%** |
| 기존 이어 묻는 대화 80개(회귀 확인): 맞음 | 75.4~76.5% | **79.6%** |

## 7. 2차를 에이전트로 — [에이전트 보고서](reports/2026-10-26-agent.md)

2차(후보 30권에서 고르기)를 한 번의 호출 대신, 도구 `answer`·`search_again`(맞는 책이 적으면 새 낱말로 한 번 더 찾기)·`ask_user`(두 갈래로 읽히면 되묻기, 화면에 버튼)를 쓰는 Haiku로 만들어 봄. 새 질문 72개(애매한 질문, 애매하게 이어 묻기, **3턴 「앞 주제 둘 합치기」**, 책이 적은 주제, 분명한 질문), 되물으면 가상 사용자(Haiku)가 숨긴 「원한 책」에 맞춰 답함, Sonnet 채점, 방식마다 두 번 돌린 평균.

방식: **한 번의 호출** = 운영 방식(2차 Haiku 호출 1번으로 고르기 JSON). **에이전트(0권)** = 도구 루프, 맞는 책이 0권일 때만 `search_again`. **에이전트(3권 미만)** = 맞는 책이 3권보다 적으면 `search_again`.

| 기준선 | 방식 | 맞음 | 맞는 카드/질문 | 틀린 카드/질문 | 0장(72개 중) | 첫 글 | 검색 1,000번 |
|---|---|---|---|---|---|---|---|
| v1.16.2 | 한 번의 호출 | 72.5% | 3.8 | 1.42 | 14.5 | — | — |
| v1.16.2 | 에이전트(0권) / 에이전트(3권 미만) (한 번씩) | 80.2 / 82.4% | 4.7 / 4.9 | 1.15 / 1.04 | 5 / 5 | — | — |
| **v1.16.3** | 한 번의 호출 | 77.0% | 4.0 | 1.19 | 9.5 | **5.1초** | **$1.40** |
| **v1.16.3** | 에이전트(0권) / 에이전트(3권 미만) | 77.9 / 80.1% | 4.4 / 4.6 | 1.24 / 1.15 | 7.5 / 9.0 | 9.4 / 9.8초 | $1.85 / $1.96 |

→ 처음(v1.16.2)에는 에이전트가 8~10%p 이겼고 합치기는 맞는 카드가 1.5 → 4.9장. 그런데 같은 날 한 번의 호출에 「앞 질문들을 이어 붙여 찾는」 규칙을 더한 v1.16.3이 나와([3-6](reports/2026-10-26-ml-first-call-decisions.md)), 그 위에서 다시 재니 **차이가 흔들림(±5%p) 안으로 줄고**, 첫 글은 두 배 늦고, 돈은 32~40% 더 듦 → **켜지 않음**. 남은 이득은 합치기·이어 묻기(합치기 맞는 카드 2.7 → 4.2, 3권 미만 방식). 분명한 질문에서는 네 번 모두 되묻기 0번. **배운 것: 기준선이 바뀌면 다시 잰다 — 처음 숫자로 내보냈다면 비용만 늘었을 것.**

**그래서 되묻기만 한 번의 호출에** (2차 고르기 JSON 맨 앞에 `ask` 칸, [보고서 10절](reports/2026-10-26-agent.md)): 전체 맞음 77.0 → 79.6%, **애매한 질문 69.4 → 77.8%, 맞는 카드 4.2 → 5.6장**, 분명한 질문 되묻기 0번, 되묻지 않은 질문의 첫 글 5.1 → 5.4초·비용 +3%. 에이전트에서 쓸모 있던 한 가지만 가장 싼 자리로 옮긴 것.

**운영에 넣은 조합 (v1.17.0)** — 되묻기 + Haiku 생각 끄기 + 프롬프트 캐싱, 10만 권 위 두 번 평균([보고서 11절](reports/2026-10-26-agent.md)): 맞음 78.0 → **80.6%**, 애매한 질문 66.7 → **78.8%**, 틀린 카드 1.32 → **1.02장**, **첫 글 4.0 → 2.3초**, 출력 토큰 절반. 응답 시간을 단계별로 재 보니 검색은 0.45초뿐이고 나머지가 Haiku의 「생각」이라는 데서 출발. 생각을 꺼도 부정어·조건 질문(57문항 종류별)은 그대로였고, 대가는 맞는 카드(2~3점) 수(57문항 질문당 6.7 → 5.8장, [`ask-back-final-2026-10-26.md`](../reports/ai-search-eval/ask-back-final-2026-10-26.md)). 72문항 묶음 중 합치기는 87.6 → 72.5%, 책이 적은 주제는 66.7 → 56.6%로 내려감(묶음 12~15개라 흔들림이 크지만 남은 일).

- **검색 속도는 빨라지지 않음**: 「소설」 140 → 141ms, 「기후 위기」 40 → 34ms. 표가 메모리에 있어 시간은 읽는 양이 아니라 LIKE 계산이 정함. 「네 낱말」 검색은 표를 정리한 뒤 실행 계획이 바뀌어 12 → 41ms로 느려짐(정리만 한 표에서도 같음) — Haiku의 몇 초에 비하면 작지만 운영 로그 `keyword` 단계로 지켜볼 일.
- 예상한 이득(빈 공간을 함께 읽어 느림)은 숫자로 나오지 않았고, 재다가 찾은 정렬 규칙 문제가 실제 이득.

## 11. 첫 글 시간 줄이기 (v1.19.0) — [첫 글 시간](reports/2026-10-27-latency.md)

**출발점**: 답을 SSE로 흘리므로 사용자가 기다리는 것은 첫 글. 운영 로그의 단계별 시각(`steps encode=… llm-first=…`)으로 쪼개 보니 요청 → Haiku 첫 토큰이 약 1.91초, 그중 Haiku 앞의 준비가 약 0.57초였고, 그 안의 낱말 검색(176ms)과 표지·요약 읽기는 앞 단계를 기다릴 이유가 없는 일이었음.

**먼저 Haiku 쪽을 따로 잼**(같은 지시문·후보로 Haiku만 15번씩): 바닥값 0.77초, 입력을 줄이거나 캐싱을 꺼도 첫 토큰은 그대로, JSON 형식 강제(`output_config.format`)가 +0.25~0.4초, 되묻기 칸이 head를 0.05초(느린 10%는 0.6초) 늦춤 → 프롬프트 줄이기는 하지 않고, **기다림을 겹치는 쪽**으로.

| 문제 | 원인 | 고친 방법 | 결과 (v1.18.0 → 고친 판) |
|---|---|---|---|
| 낱말 검색이 질문 벡터·1차 신경망·이웃 뒤에야 시작 | 계획(낱말)이 1차 신경망에서 나온다고 보고 순서대로 짬. 그런데 첫 질문의 낱말(`QuestionWords`)은 질문만으로 정해짐 | 질문 벡터를 요청할 때 같은 낱말로 낱말 후보 SQL을 가상 스레드에서 같이 시작, 1차가 정한 낱말이 같고 뺄 책이 없을 때만 그 결과를 씀(후보는 전과 같음) | 5낱말 이상 첫 질문의 낱말 검색 대기 **102 → 0ms**(40번 중 36번 이미 끝남) |

| 되묻지 않을 질문도 빈 되묻기 칸부터 씀 | 되묻기를 켜면 모든 질문에 되묻기 형식(`ask`가 `head` 앞) | 되묻기 형식은 4낱말 이하 첫 질문·이어지는 질문에만 | Haiku 첫 토큰 → 첫 글 **108 → 20ms**, 느린 10% **199 → 28ms** |
| **5낱말 이상 첫 질문** | | | 첫 글 **1.68 → 1.43초**, 느린 10% **2.15 → 1.75초** |
| **전체** | | | 첫 글 1.84 → 1.69초, 카드 맞음 **91 → 92%**, 틀린 카드 0.42 → 0.41장(그대로) |

- **운영에서 (같은 첫 질문 24개, 배포 전후)**: 5낱말 이상 첫 질문 첫 글 **2.63 → 2.06~2.25초**(v1.19.0 두 번), Haiku 호출까지 준비 505 → 302~356ms, 서버 첫 토큰 → 사용자 첫 글 741 → 504~533ms. 로컬(−0.25초)보다 크게 준 것은 운영의 낱말 검색·카드 읽기가 더 느려 겹친 몫이 컸기 때문([첫 글 시간 6절](reports/2026-10-27-latency.md)).
- 짧은 질문(4낱말 이하)은 되묻기를 지키려고 그대로 둠. 되물을 때 첫 글은 되묻는 말이 다 써진 뒤라 2.4초대.
- 가장 큰 남은 몫인 형식 강제(+0.25~0.4초)는 JSON이 깨지는 비율을 재기 전에는 빼지 않음.

## 12. 대화 점검과 다음 계획 (계획, 사이클 26 뒤) — [대화 점검](reports/2026-10-28-talk-review.md)

**출발점**: 사용자가 직접 써 보니 「우리가 손으로 바꾼 문구가 어색함」, 「책 정보만 하나하나」, 「대화가 어색함」. 운영과 같은 설정의 로컬 서버에 일상 말·엉뚱한 말·이어 묻기를 섞은 **대화 37개(57턴)**를 보내고, 코드에서 모델 글이 그대로 보이지 않는 곳을 줄 번호까지 찾음.

| 찾은 것 | 숫자 | 원인 | 고칠 안 |
|---|---|---|---|
| 모델이 잘 쓴 머리말을 웹이 지우고 「맞는 책을 찾지 못했어요」로 | 57턴 중 **5턴** | 고른 책이 0권이면 웹이 머리말을 숨김 | 모델 글을 그대로 두고, 고정 문구는 빈 머리말일 때만 |
| 책 밖 말에 대화와 상관없는 고정 되묻기 | **6턴**(「잠이 안 와」에 「경제 교양서」 예시) | 모델을 부르지 않는 고정 문구 + 예시 10개 중 무작위 3개 | 짧은 모델 호출 하나로 답하고 대화에 맞춘 예시로 책 이야기에 이끌기 |

**먼저 고친 것(2026-10-29, v1.20.5)** — [대화를 가리키는 말](reports/2026-10-29-talk-refs.md): 「모르겠어」·「그거 말고」·「아까 이야기한 거」를 정규식 세 개와 대화 낱말 쪼개기(동적 계획법)로 알아보고, 가리킨 주제로 검색하며 2차 지시문에 「대화 메모」 한 줄을 붙임. 대화 27개(40턴)를 Sonnet 4개로 채점: **통과 23 → 40 / 40**, 틀린 카드 52 → 2, 「목록」이라는 말 3 → 0. 보통 질문 80문항은 카드 맞음 92% → 90%(바꾼 길을 지나지 않는 합치기 6문항의 흔들림). 운영에서도 8개 대화 22 / 23턴 통과, 첫 글 시간은 그대로(중간 2.34초).

- 숫자로 다시 잴 것: 같은 57턴 + 규칙 시험 80문항(카드 맞음 92% 유지) + 책 밖 말 30개 + 이어 묻기 대화. 고친 뒤 이 절에 전후를 채움.

## 13. 배운 것

- **기준선이 바뀌면 다시 잰다.** 에이전트는 v1.16.2 위에서 8~10%p 이겼지만, 같은 날 한 번의 호출을 고친 v1.16.3 위에서는 흔들림 안이었음. 처음 숫자로 내보냈다면 비용만 늘었을 것.
- **한 번 돌린 차이는 믿지 않는다.** 「72.2 → 75.4%」는 3번씩 다시 돌리니 흔들림 안(74.3 vs 76.2%)이었고, 흔들림을 넘는 것(조건 더하기 67 → 76%)만 남김.
- **잘한 것처럼 보이는 숫자를 의심한다.** 길 나누기 「98~100%」는 늘 「아니오」만 해도 97%가 나오는 칸이었음 → 유형별로 다시 잼.
- **채점자도 잰다.** Sonnet 점수를 Opus로 다시 매겨 맞음/틀림 88% 일치, Opus가 조금 후함 → Sonnet 점수는 부풀려지기보다 엄한 쪽.
- **시험 도구도 틀릴 수 있다.** 카드 글은 스트림의 다른 이벤트(`card-delta`)로 와서, 한동안 「글에 연도를 썼는지」를 머리말로만 셌음 → 고치고 다시 확인해 기록에 남김.
- **지표에 없는 것은 나빠져도 모른다.** 생각 끄기는 맞음·속도로만 재서, 되묻기가 줄어든 것을 사용자가 「사진」으로 찾을 때까지 몰랐음 → 규칙마다 판정 칸을 두는 규칙 시험을 만듦.
- **규칙은 코드 경로와 함께 읽는다.** 지시문만 보면 멀쩡했지만, 그 줄이 쓰이는 턴에 코드는 다른 지시문을 보내고 있었음(죽은 지시문).
- **재 보면 원인이 다른 곳에 있다.** 「빈 공간을 읽어서 느리다」는 예상 대신, 재다가 「정렬 규칙 때문에 통계가 400초」를 찾음. 줄인 크기는 검색 시간을 바꾸지 못했음.
- **사용자가 찾은 사례를 시험으로 만든다.** 6절의 네 가지는 모두 운영에서 사용자가 찾은 것이고, 같은 꼴의 질문 50개로 늘려 고친 전후를 잼.

## 14. 한계 (포트폴리오에 같이 쓸 것)

- 질문 57개, 한 사람이 만든 질문. 채점은 사람 대신 Sonnet(같은 채점표를 모든 안에 씀).
- 대부분 안은 한 번씩만 돌림. 흔들림 폭(±3%p)은 두 안을 두 번 돌려 잰 값.
- 「○○ 같은 책」은 9개뿐이라 숫자가 크게 흔들릴 수 있음.
- 채점자 확인은 사람이 아니라 다른 모델(Opus)로 함: 카드 100장에서 맞음/틀림이 Sonnet과 88% 같음(Opus가 조금 후함). 사람이 직접 본 점수는 없음.
- 이어 묻는 질문 시험(대화 80개)은 rule·relation을 3번씩 돌림: 전체 맞음의 폭이 4%p 안팎이라 2%p 차이는 「비슷함」으로 읽어야 함. 관계마다 10~20개라 칸마다는 더 흔들림.
- 속도·비용은 로컬 PC에서 잰 값(2차 Haiku는 실제 API). 운영 앞뒤 값은 질문이 서로 달라 참고만.
- 3번 이어지는 대화(「위에 말한 두 개」, 「둘 섞은 느낌」)는 운영에서 사용자가 찾은 뒤 50개 시험을 만들어 고침(합치기 카드 0장 12 → 1 / 25, [3-6](reports/2026-10-26-ml-first-call-decisions.md)). 한 번씩 돌린 값이고, 「앞 질문 여러 개」는 신호 말 규칙으로 잡음(모델 아님).
- 에이전트 시험(7절)은 방식마다 두 번 돌림: 같은 한 번의 호출이 73.5 / 80.5%로 흔들려 5%p 안팎은 「비슷함」. 묶음마다 10~20개라 묶음 숫자는 더 흔들림(합치기 56 / 65%). 되묻기 답은 가상 사용자(Haiku)가 함 — 실제 사람이 되묻기를 어떻게 느끼는지는 재지 않음.
- 규칙 시험(9절)의 「되물어야 한다 / 되묻지 말아야 한다」 기대값은 한 사람이 정함. 「강아지」처럼 갈래가 실제로 있는 말은 되묻는 편이 맞을 수도 있음. 판마다 두 번만 돌렸고 묶음마다 2~16문항이라 묶음 숫자는 크게 흔들림.
- 표 줄이기(10절)는 로컬 PC의 복사본에서 잼. 운영 서버(ARM 2코어)의 ANALYZE 시간은 로그의 시작·끝 시각(15분)으로만 확인함.
