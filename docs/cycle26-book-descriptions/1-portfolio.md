## 1. AI 검색: 같은 질의가 쌓이면 20배 느려지던 실행 계획 (v1.20.1)

**상황.** 배포 뒤 AI 검색 첫 글 시간을 다시 재니, 서버를 켠 직후 두 번은 괜찮다가 세 번째부터 여러 낱말 질문(「소설 말고 위로가 되는 책」 등)의 낱말 찾기가 3~5.4초 걸렸다. 한 낱말 질문은 0초였다.

**원인 찾기.**
- 처음 의심: 배포 때 새 표 통계(ANALYZE)가 바뀌어 실행 계획이 바뀌었다. 운영 DB `pg_stat_user_tables`를 보니 배포 뒤 ANALYZE는 없었다 → 아님.
- 서버가 이 질문에서 뽑는 낱말은 `QuestionWords` 규칙(끝말 떼기, 한 글자·요청 말 빼기)으로 「소설」·「위로」 두 개. 그 SQL을 운영 DB에서 `PREPARE` 한 뒤 `plan_cache_mode`를 바꿔 가며 `EXPLAIN ANALYZE`(계획 도서관 = 표의 모든 도서관 2,455곳):

| 계획 | 맞는 줄 예상 → 실제 | 실행 노드 | 계획 도서관 수 세기 | 예상 비용 | 시간 |
|---|---|---|---|---|---|
| custom plan(값을 넣고 세운 계획) | 18,906 → 16,418 | Parallel Bitmap Heap Scan → Gather Merge → Incremental Sort | 위쪽 606줄만, 배열 비교는 해시 | 13,120 | **0.24초** |
| generic plan(값 없이 세운 계획) | **8 → 16,418** | Bitmap Heap Scan → Sort | 16,418줄 모두, 배열을 줄마다 처음부터 훑음 | **2,376** | **5.17초** |

- 예상이 틀린 까닭(선택도 = 조건을 통과할 줄의 비율 추정):
  - custom plan은 `'%소설%'`을 알기 때문에 `pg_stats.histogram_bounds`(ANALYZE가 뽑아 둔 `search_text` 표본 101개 중 양 끝을 뺀 99개)에 패턴을 직접 대 본다. 99개 중 16개가 「소설」을 품어 16/99 × 76,759 = **12,405줄**(실제 12,200), 「위로」는 10/99 → **7,753줄**(실제 4,823).
  - generic plan은 패턴이 `$1`이라 표본에 대 볼 수 없어, `LIKE`의 정해진 기본 선택도 `DEFAULT_MATCH_SEL` = 0.005를 쓴다 → 낱말마다 76,759 × 0.005 = **384줄**.
  - 두 `LIKE`의 OR: 독립이라 보고 0.005 + 0.005 − 0.005 × 0.005 = 0.009975. `library_ids && $3`도 배열을 모르니 겹침 기본 선택도 `DEFAULT_OVERLAP_SEL` = 0.01. 곱하면 76,759 × 0.009975 × 0.01 ≈ **8줄**. 실제로는 「소설」 15.9%, 「위로」 6.3%, 계획 도서관 조건은 모든 줄이 통과(1.0)라 16,418줄 — **약 2,000배 차이**.
- 구조: JDBC 드라이버(pgjdbc)는 같은 SQL을 한 연결에서 5번(`prepareThreshold`) 쓰면 서버 쪽 준비문(server-side prepared statement)으로 바꾼다. PostgreSQL은 준비문을 5번 custom plan으로 돌린 뒤 generic plan을 만들어, 그 예상 비용이 custom plan 평균보다 작으면 generic plan을 쓴다(`plan_cache_mode = auto`, `plancache.c`의 `choose_custom_plan`). 8줄 예상 덕에 generic plan은 2,376으로 custom plan 13,120보다 싸 보여 뽑혔다.
- 실제로 느린 까닭: generic plan은 8줄이라 믿고 모든 줄에 `plan_count` 서브플랜(줄마다 `unnest(library_ids)` 약 72개 × `= ANY($3)` 2,455개)을 돌린다. `$3`이 상수가 아니라 PG14부터의 해시 비교(hashed ScalarArrayOpExpr)를 못 쓰고 배열을 처음부터 훑어 한 줄 0.30ms × 16,418줄 ≈ 5초. custom plan은 점수 순으로 먼저 줄 세운 뒤 위쪽 606줄에만, 해시로 0.02ms씩.
- 모든 낱말을 빈칸으로만 자른 다섯 낱말 꼴(「소설」·「말고」·「위로가」·「되는」·「책」, 서버가 실제로 쓰는 낱말은 아님)로도 재 보면 custom 0.64초 / generic 11.2초(예상 19줄 → 실제 35,731줄)로, 맞는 줄이 많을수록 벌어진다.
- 낱말 검색 SQL은 낱말 수·핵심어 수가 같으면 글이 같아, 서버가 오래 켜져 있으면 연결마다 문턱을 넘는다. 측정 순서(직후 2회 정상, 3회째부터 느림)와 맞았다.
- 옛 표에도 다섯 낱말 꼴을 돌려 0.44초 / 11.1초 → **배포가 만든 문제가 아니라 전부터 숨어 있던 문제**였음을 확인.

**자세한 해설.** 용어, 추정 계산, 실행 노드, 재는 SQL 전부: [3-postgres-generic-plan.md](3-postgres-generic-plan.md).

**고친 것.** 이 질의 하나만 읽기 전용 트랜잭션 안에서 `SET LOCAL plan_cache_mode = force_custom_plan`을 먼저 실행한다. `SET LOCAL`이라 트랜잭션이 끝나면 원래대로, 다른 질의에는 영향 없음. 전역 설정이나 드라이버 설정(`prepareThreshold=0`)을 바꾸지 않은 이유: 다른 질의는 generic plan이 이득이고, 문제는 이 질의에만 있었다.

**확인.** 시험 `AiSearchIndexTests.repeatedSearchesKeepCustomPlans`: 같은 검색 12번 뒤 `pg_prepared_statements.generic_plans` = 0. 고침을 빼고 돌리면 이 시험이 실패하는 것을 먼저 확인했다. 운영 효과(dev 24, 같은 첫 질문 24개 × 4회 연달아, v1.20.1 2026-10-29 09:2x~09:4x): **1초 넘은 낱말 검색 0번**, 첫 글 느린 10% **5.2~5.8초 → 2.76~3.05초**(v1.20.0 r3·r4 → v1.20.1), 첫 글 중간 2.10~2.30초, 5낱말 이상 첫 글 중간 1.9~2.1초(v1.19.0 2.1~2.2초). 회차별 표: [../aisearch/reports/2026-10-27-latency.md](../aisearch/reports/2026-10-27-latency.md) 7절.

**보여 주는 것.** 증상(시간)에서 출발해 가설을 하나씩 운영 데이터로 지움 → 드라이버와 DB 플래너의 상호작용까지 내려가 재현 → 고침 범위를 질의 하나로 좁힘 → 재발을 잡는 시험.

## 2. DB 마이그레이션: 복사 295초 → 4.2초

**상황.** 책 설명 표 다섯을 `catalog`로 옮기는 Liquibase changeset을 운영과 같은 크기의 DB 복사본에서 미리 돌리니 복사 단계가 295초. 이 동안 서버가 뜨지 않으므로 그대로면 배포 중 약 5분 멈춤.

**원인.** 단계를 나눠 재니 INSERT 다섯은 합 9초, **`ANALYZE catalog.book_summary`가 388초**(따로 잼). 한글 요약 68,414줄의 통계를 DB 기본 정렬 규칙(en_US.utf8)으로 계산하는 비용. 검색 표는 색인이 있는 채로 넣어 8.3초.

**고친 것.** 요약 칸을 `COLLATE "C"`로(사람에게 정렬해 보이지 않는 칸이라 잃는 것 없음) → ANALYZE 0.06초. 검색 표의 pg_bigm 색인은 데이터를 넣은 뒤 만들기로. 아직 어디에도 배포하지 않은 changeset이라 프로젝트 규칙(PRE_DEPLOYMENT)대로 고쳐 다시 적용.

**결과.** 복사 **4.2초**(PC), 운영 배포에서 **7.7초**(226,038줄), 서버 시작 28.3초. 옮긴 다섯 표의 줄 수·글자를 옛 표와 비교해 모두 같음(요약 69,188, 표지 80,091, 검색 76,759).

## 3. 같은 책 요약을 네 화면에서 하나로

**상황.** 추천목록 책 창, 책첵 추천, AI 검색 카드, 책 상세가 요약을 서로 다른 표에서 읽어, 같은 책에 다른 글이 보일 수 있었다(추천목록 전용 요약 글).

**고친 것.** 요약·표지·꼬리표·프로필·AI 검색 줄을 `catalog` 모듈의 표와 공개 API(`BookTexts`, `CoverUrls`, `BookProfiles`, `AiSearchIndex`) 한 곳으로 모으고, 네 화면이 모두 그 API를 읽게 함. 다른 모듈은 표를 직접 읽지 않음(Spring Modulith 경계). 추천목록 전용 요약만 있던 책 774권은 새 요약을 미리 만들어 채움.

**확인.** 운영에서 「달러구트 꿈 백화점」이 네 API(`picks/shelf`, `for-you/books`, `ai-searches/stream`, `books/1172`)에서 글자까지 같음. 진열 6권·AI 검색 카드 5권도 책 상세와 모두 같음.

## 4. 표지 113만 장을 S3 + CloudFront로

**상황.** 표지 그림을 운영 서버 디스크(남은 공간 약 9GB)에 두고 서버가 직접 내보냈다. 전체 표지(약 113만 장)를 올리기엔 디스크와 서버 부담이 맞지 않음.

**고친 것.** 비공개 S3 버킷 + CloudFront(OAC)로 옮기고, 웹은 CloudFront 주소로 그림을 받음(CSP `img-src`에 그 주소만 더함). S3에는 PC만 올림(운영 서버에는 S3 권한 없음). 차례는 「그림 먼저 올리고, 올린 그림만 책과 연결」이라 깨진 그림이 보이지 않음. 연결 파일은 첫 줄 `# export_id=`로 책 번호를 만든 가져오기를 밝혀, 다른 가져오기 기준의 파일은 넣기 명령이 거절.

**숫자.** 폴더 하나씩 `aws s3 cp --recursive` 한 줄은 약 25장/초 → 폴더를 8묶음으로 나눠 동시에 약 170장/초(35분에 362,076장, 2026-10-29 09:16). 8개가 90~105분에 모두 끝남(256폴더, 실패 0). 비용 어림 PUT 113만 건 약 $6.2(시드니).

**연결과 확인.** 올린 뒤 S3 목록(1,130,143개)과 연결할 그림(1,128,687장)을 대조해 **빠진 것 0**을 확인하고서야 책과 이었다(`cover_file` 1,145,754줄을 25만 줄씩 다섯 파일로, 파일마다 24~30초). 이미 있던 80,091권의 연결은 새 파일과 **모두 같음**을 먼저 확인. 결과: 운영 `catalog.book_cover` 1,145,754권(그림 1,128,687장, 표 136MB), 책 없는 줄 0, AC-11(S3 객체 수 ≥ 서로 다른 그림 수) 통과, 새로 이어진 책 표지가 CloudFront에서 200.

## 5. 흔한 낱말 질문을 더 빠르게: 질의 9판을 24경우로 재고 운영에서 다시 고침 (v1.20.3, v1.20.4)

**상황.** v1.20.1 뒤 남은 가장 느린 낱말 찾기는 「소설」처럼 흔한 한 낱말 질문(운영 253~347ms). 맞은 1만 2천 권이 점수가 같아 모든 책의 「내 도서관 수」를 세야 했다.

**한 것.**
- 「내 도서관 수 세기」를 PostgreSQL 확장 intarray의 정렬 배열 교집합(C 함수)으로, 낱말 점수를 `LIKE` 대신 `strpos`로 바꾼 판 8가지를 만들어, 낱말 6가지 × 계획 도서관 크기 3~4가지에서 재고, 판마다 결과 30줄의 md5로 **답이 같은지** 확인(모두 같음).
- PC 결과로 고른 판(V7)을 v1.20.3으로 올린 뒤 운영에서 같은 도구로 다시 재니, 한 낱말(347 → 208ms)과 작은 계획(200곳 이하)은 크게 빨라졌지만 **계획 도서관 1,000곳 이상의 여러 낱말 질문 6경우가 11~42ms 느려졌다**.
- 실행 계획으로 까닭을 찾음: 지금 질의는 점수로 먼저 정렬해 필요한 606권만 세는데(Incremental Sort), 새 판은 맞은 1만 6천 권을 모두 센다. 한 번이 싸도 큰 계획 배열에선 모두 세는 쪽이 진다. 함수 비용 선언(COST 1,000/3,000/10,000)으로 계획을 바꿔 보려 했으나 나아지지 않았다.
- 그래서 **경우를 나눔**(v1.20.4): 한 낱말이거나 계획 도서관 500곳 이하면 intarray 함수, 아니면 지금 방식. 운영 결과(24경우): 합 **2,773 → 2,006ms(−28%)**, 가장 느린 경우 **343 → 204ms(−41%)**, 이전보다 10ms 넘게 느린 경우 **0**, 답 모두 같음.

**보여 주는 것.** 측정으로 판을 고르고, 운영에서 다시 재서 PC가 못 보여 준 회귀를 찾고, 실행 계획으로 원인을 설명한 뒤 경우를 나눠 고침. 확장은 따로 된 스키마에 두어 다른 질의의 연산자를 바꾸지 않음. 전체: [4-keyword-query-speed.md](4-keyword-query-speed.md).
