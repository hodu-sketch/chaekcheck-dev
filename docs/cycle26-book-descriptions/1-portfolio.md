## 1. AI 검색: 같은 질의가 쌓이면 11초가 되던 실행 계획 (v1.20.1)

**상황.** 배포 뒤 AI 검색 첫 글 시간을 다시 재니, 서버를 켠 직후 두 번은 괜찮다가 세 번째부터 여러 낱말 질문(「소설 말고 위로가 되는 책」 등)의 낱말 찾기가 3~5.4초 걸렸다. 한 낱말 질문은 0초였다.

**원인 찾기.**
- 처음 의심: 배포 때 새 표 통계(ANALYZE)가 바뀌어 실행 계획이 바뀌었다. 운영 DB `pg_stat_user_tables`를 보니 배포 뒤 ANALYZE는 없었다 → 아님.
- 같은 SQL을 운영 DB에서 `PREPARE` 한 뒤 `plan_cache_mode`를 바꿔 가며 `EXPLAIN ANALYZE`:

| 계획 | 실행 노드 | 계획 도서관 수 세기 | 시간 |
|---|---|---|---|
| custom plan(값을 넣고 세운 계획) | Parallel Seq Scan → Incremental Sort | 위쪽 212줄만, 배열 비교는 해시 | **0.64초** |
| generic plan(값 없이 세운 계획) | Bitmap Heap Scan(pg_bigm 색인) → Sort | 맞은 35,731줄 모두, 배열을 줄마다 처음부터 훑음 | **11.2초** |

- 구조: JDBC 드라이버(pgjdbc)는 같은 SQL을 한 연결에서 5번(`prepareThreshold`) 쓰면 서버 쪽 준비문(server-side prepared statement)으로 바꾼다. PostgreSQL은 준비문을 5번 custom plan으로 돌린 뒤 generic plan을 만들어, 예상 비용이 custom plan 평균보다 싸면 그것을 쓴다(`plan_cache_mode = auto`). 값을 모르는 `LIKE $1`의 선택도를 기본값으로 잡아 맞는 줄을 **19줄**로 예상(실제 35,731줄)했고, 그래서 generic plan의 비용이 4,815로 custom plan(약 15,600)보다 싸 보였다.
- 낱말 검색 SQL은 낱말 수·핵심어 수가 같으면 글이 같아, 서버가 오래 켜져 있으면 연결마다 문턱을 넘는다. 측정 순서(직후 2회 정상, 3회째부터 느림)와 맞았다.
- 옛 표에도 같은 질의를 돌려 0.44초 / 11.1초 → **배포가 만든 문제가 아니라 전부터 숨어 있던 문제**였음을 확인.

**고친 것.** 이 질의 하나만 읽기 전용 트랜잭션 안에서 `SET LOCAL plan_cache_mode = force_custom_plan`을 먼저 실행한다. `SET LOCAL`이라 트랜잭션이 끝나면 원래대로, 다른 질의에는 영향 없음. 전역 설정이나 드라이버 설정(`prepareThreshold=0`)을 바꾸지 않은 이유: 다른 질의는 generic plan이 이득이고, 문제는 이 질의에만 있었다.

**확인.** 시험 `AiSearchIndexTests.repeatedSearchesKeepCustomPlans`: 같은 검색 12번 뒤 `pg_prepared_statements.generic_plans` = 0. 고침을 빼고 돌리면 이 시험이 실패하는 것을 먼저 확인했다. 운영 효과는 배포 뒤 dev 24가 같은 질문 24개를 4회 돌려 잰다(결과는 [2-dev-record.md](2-dev-record.md) 4절에 더함).

**보여 주는 것.** 증상(시간)에서 출발해 가설을 하나씩 운영 데이터로 지움 → 드라이버와 DB 플래너의 상호작용까지 내려가 재현 → 고침 범위를 질의 하나로 좁힘 → 재발을 잡는 시험.

## 2. DB 마이그레이션: 복사 295초 → 4.2초

**상황.** 책 설명 표 다섯을 `catalog`로 옮기는 Liquibase changeset을 운영과 같은 크기의 DB 복사본에서 미리 돌리니 복사 단계가 295초. 이 동안 서버가 뜨지 않으므로 그대로면 배포 중 약 5분 멈춤.

**원인.** 단계를 나눠 재니 INSERT 다섯은 합 9초, **`ANALYZE catalog.book_summary`가 388초**(병렬 측정 포함). 한글 요약 68,414줄의 통계를 DB 기본 정렬 규칙(en_US.utf8)으로 계산하는 비용. 검색 표는 색인이 있는 채로 넣어 8.3초.

**고친 것.** 요약 칸을 `COLLATE "C"`로(사람에게 정렬해 보이지 않는 칸이라 잃는 것 없음) → ANALYZE 0.06초. 검색 표의 pg_bigm 색인은 데이터를 넣은 뒤 만들기로. 아직 어디에도 배포하지 않은 changeset이라 프로젝트 규칙(PRE_DEPLOYMENT)대로 고쳐 다시 적용.

**결과.** 복사 **4.2초**(PC), 운영 배포에서 **7.7초**(226,038줄), 서버 시작 28.3초. 옮긴 다섯 표의 줄 수·글자를 옛 표와 비교해 모두 같음(요약 69,188, 표지 80,091, 검색 76,759).

## 3. 같은 책 요약을 네 화면에서 하나로

**상황.** 추천목록 책 창, 책첵 추천, AI 검색 카드, 책 상세가 요약을 서로 다른 표에서 읽어, 같은 책에 다른 글이 보일 수 있었다(추천목록 전용 요약 글).

**고친 것.** 요약·표지·꼬리표·프로필·AI 검색 줄을 `catalog` 모듈의 표와 공개 API(`BookTexts`, `CoverUrls`, `BookProfiles`, `AiSearchIndex`) 한 곳으로 모으고, 네 화면이 모두 그 API를 읽게 함. 다른 모듈은 표를 직접 읽지 않음(Spring Modulith 경계). 추천목록 전용 요약만 있던 책 774권은 새 요약을 미리 만들어 채움.

**확인.** 운영에서 「달러구트 꿈 백화점」이 네 API(`picks/shelf`, `for-you/books`, `ai-searches/stream`, `books/1172`)에서 글자까지 같음. 진열 6권·AI 검색 카드 5권도 책 상세와 모두 같음.

## 4. 표지 113만 장을 S3 + CloudFront로

**상황.** 표지 그림을 운영 서버 디스크(남은 공간 약 9GB)에 두고 서버가 직접 내보냈다. 전체 표지(약 113만 장)를 올리기엔 디스크와 서버 부담이 맞지 않음.

**고친 것.** 비공개 S3 버킷 + CloudFront(OAC)로 옮기고, 웹은 CloudFront 주소로 그림을 받음(CSP `img-src`에 그 주소만 더함). S3에는 PC만 올림(운영 서버에는 S3 권한 없음). 차례는 「그림 먼저 올리고, 올린 그림만 책과 연결」이라 깨진 그림이 보이지 않음. 연결 파일은 첫 줄 `# export_id=`로 책 번호를 만든 가져오기를 밝혀, 다른 가져오기 기준의 파일은 넣기 명령이 거절.

**숫자.** 폴더 하나씩 `aws s3 cp --recursive` 한 줄은 약 25장/초 → 폴더를 8묶음으로 나눠 동시에 약 170장/초(35분에 362,076장, 2026-10-29 09:16). 비용 어림 PUT 113만 건 약 $6.2(시드니). 끝난 뒤의 장 수·시간·S3 객체 수는 [2-dev-record.md](2-dev-record.md) 3절.
