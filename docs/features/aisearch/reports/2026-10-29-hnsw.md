# 가까운 책 찾기: 지금의 전수 비교 vs pgvector HNSW (2026-10-29)

> **이 기록은 2026-10-29(v1.22.x) 기준입니다.** 「지금」은 그때를 말합니다. v1.23.0부터 운영은 책 줄 238,392개를 깔때기(`vector.search.mode: funnel`)로 찾습니다. 지금 동작은 [1-how-it-works 4-4절](../1-how-it-works.md#4-4-가까운-책-nearest).

AI 검색의 「가까운 책」 단계(`BookVectorFile.nearest`)를 PostgreSQL + pgvector HNSW 색인으로 바꿀지 판단하려고 잰 기록입니다. 모든 숫자는 **잰 값**과 **추정**을 따로 적었습니다. 추정에는 [추정]을 붙였습니다.

이어지는 기록: 20만\~100만 권에서 고를 네 길(Java binary 깔때기, halfvec HNSW, binary HNSW, 전용 벡터 DB)과 binary·int4 거르기 재현율은 [책 수 늘리기 보고서](2026-10-30-vector-scaling.md).

## 0. 결론 먼저

- **지금(81,078권)은 전수 비교를 유지합니다.** 운영에서 nearest는 중간값 97ms이고(응답 시간 보고서), 내 PC에서 같은 코드로 잰 값은 중간값 66.4ms입니다. HNSW는 DB 안에서 10\~15ms로 빠르지만, (1) 상위 120권 재현율이 0.87\~0.97이라 같은 답을 주지 못하고, (2) 디스크 0.45\~1.1GB가 더 들고, (3) 2GB 서버(t4g.small)에서 색인이 메모리에 다 올라가지 못하면 80\~220ms로 오히려 느려집니다(3-6절).
- **바꿀 때를 정하는 기준은 책 수 약 15만\~20만 권입니다 [추정].** 운영 nearest가 200ms를 넘는 지점(97ms × N / 81,078 ≥ 200 → N ≈ 167,000)이고, 그때 힙 사용이 약 170MB(-Xmx640m의 약 27%)가 됩니다. 30만 권이면 운영 약 400ms·힙 311MB [추정], 100만 권이면 운영 약 1초·힙 1.04GB로 지금 힙(640MB)에 들어가지 않습니다(4절).
- 그때 바꾸더라도 조건이 붙습니다: `halfvec(1024)` + HNSW(m 16, ef_construction 64), `hnsw.ef_search` ≥ 200(또는 `hnsw.iterative_scan`), 그리고 **색인 전체가 페이지 캐시에 들어갈 RAM이 있는 DB 서버**. 30만 권이면 halfvec 색인만 약 0.82GB [추정]라 지금 2GB 서버에는 맞지 않습니다.

## 1. 지금 코드가 하는 일 (코드에서 확인)

- 파일: 모델 폴더의 `book-vectors.bin`. 운영 모델 폴더와 같은 로컬 사본 `..\chaekcheck-data\ml\aisearch-model-100k\book-vectors.bin`, **83,996,822바이트** = 머리 14바이트(`"CCBV1\n"` + count + dim, int32 LE) + 81,078 × (id int64 8 + scale float32 4 + int8 1,024). **81,078권 × 1,024차원.**
- 읽기: `BookVectorFile.read`가 파일 전체를 힙으로 읽습니다(`long[] ids`, `float[] scales`, `byte[] rows`). 잰 힙 증가 **81.3MB**, 읽기 173ms(내 PC).
- 계산(`BookVectorFile.nearest(float[] query, int limit)`): 81,078줄마다 `점수 = (Σ_{i<1024} rows[i] × q[i]) × scale[줄]`, 크기 `limit`의 최소 힙으로 상위만 남김. 단일 스레드, 스칼라 루프(Vector API 없음).
- 질문 벡터: KURE-v1 1,024차원, 길이 1로 정규화(`OnnxQuestionEncoder` 또는 운영의 `RemoteQuestionEncoder`). 책 벡터도 길이 1(int8 × scale로 되돌린 길이 0.99769\~1.00258, `make_copy_file.py` 출력)이라 점수는 코사인 유사도에 가깝습니다. 그래서 pgvector에서는 **내적(`<#>`, `vector_ip_ops`/`halfvec_ip_ops`)** 을 썼습니다(서버 점수와 같은 순서).
- 몇 개를 묻나: `AiSearchFlow`의 두 곳 모두 `vectorDepth() * 2` = **120** (`application.yml` `vector-depth: 60`).
  - `AiSearchFlow.java:767` (ML 1차 길, `mlStep`): `vectors.nearest(search, settings.vectorDepth() * 2)` → `KureQuestionVectors.nearest(float[], int)` → `books.nearest`.
  - `AiSearchFlow.java:349` (Haiku 1차 길): `vectors.nearest(searchQuestion, vectorDepth * 2)`.
  - 받은 120권은 `vectorCandidates`에서 검색 대상·제외 목록으로 거르고, 계획 도서관이 가진 책만 남겨 최대 60권(`limit(settings.vectorDepth())`)을 씁니다. 즉 「먼저 120 → 나중에 거르기」 구조이고, HNSW로 바꿔도 같은 계약(정확한 상위 120)이 필요합니다.
- 운영에서 잰 시간: 응답 시간 보고서(`docs/features/aisearch/reports/2026-10-27-latency.md` 1절, v1.18.0, 검색 8번) nearest 단계 **중간값 97ms, 최대 137ms**. 운영 백엔드는 t4g.small(ARM 2코어, 2GB), `-Xmx640m`(`deploy/prod/compose.yaml`).

## 3. pgvector HNSW (잰 값)

### 3-1. 방법

- 버림용 컨테이너 하나만 썼습니다: 이름 `chaekcheck-hnsw-bench`, 이미지 `pgvector/pgvector:pg18`(PostgreSQL **18.6**, pgvector **0.8.7**), 포트 **55432**, `--cpus 2 --memory 3g`. 프로젝트의 `db`/`db-test`(compose)와 c26 컨테이너는 건드리지 않았고, 끝나고 컨테이너와 그 익명 볼륨을 지웠습니다.
- 설정은 운영(`deploy/prod/compose.yaml`)과 같게: `shared_buffers=64MB`, `effective_cache_size=768MB`, `work_mem=4MB`. 색인 만들 때만 세션에서 `maintenance_work_mem='1GB'`, `max_parallel_maintenance_workers=1`(리더 + 1 = 2코어).
- 데이터: `scripts/aisearch/hnsw/make_copy_file.py`가 `book-vectors.bin`의 int8 × scale(서버가 점수 내는 바로 그 벡터)을 float32로 바이너리 COPY 파일(333,879,225바이트)로 씀.
  - `book_vec(id bigint primary key, embedding vector(1024) not null)` ← `COPY ... (FORMAT binary)` 5.8초.
  - `book_half` = `select id, embedding::halfvec(1024)` (2.8초) + 기본키.
- 측정: `scripts/aisearch/hnsw/pg_bench.py`(실행은 `run_pg_bench.sh <데이터폴더> [--quick] [--keep]`). 표마다 먼저 색인 없이 정확한 순차 스캔, 그다음 HNSW (m 32, ef_construction 128) → (m 16, ef_construction 64) 순서로 만들고 질문 222개를 `select id from <표> order by embedding <#> $1 limit k` 로 물음. k = 120(서버가 묻는 수)과 10. `hnsw.ef_search` 40/100/200/400, ef_search < 120이면 `hnsw.iterative_scan = 'relaxed_order'`도.
  - 「DB 시간」 = `EXPLAIN (ANALYZE)`의 Execution Time(데우기 20번 뒤 질문마다 한 번).
  - 재현율 = 서버(`BookVectorFile.nearest`)의 정확한 상위 k(`brute-gt.tsv`)와 겹친 비율.
- 원본: `chaekcheck-dev\data\aisearch-hnsw\pg-results.json`, `pg-bench.log`(222개), `pg-results-quick.json`, `pg-bench-quick.log`(앞 40개, 같은 설정, 색인은 m 16만).

### 3-2. 크기 (81,078권, 잰 값)

| | 표 본체 `pg_relation_size` | 표 전체 `pg_total_relation_size`(TOAST·기본키 포함) | HNSW 색인 `pg_relation_size` |
|---|---|---|---|
| `vector(1024)` | 4,997,120 (5MB) | **455,868,416 (435MiB)** | m16/ef64: **664,027,136 (633MiB)**, m32/ef128: 664,027,136 |
| `halfvec(1024)` | 5,013,504 (5MB) | **232,022,016 (221MiB)** | m16/ef64: **221,347,840 (211MiB)**, m32/ef128: 221,347,840 |

- 표 본체가 5MB뿐인 것은 벡터(4KB / 2KB)가 TOAST로 빠지기 때문입니다. 순수 float32는 81,078 × 4,096 = 332MB로 「약 330MB」라는 예상은 원자료 크기로는 맞지만, 실제 표는 TOAST 머리·페이지 빈칸 때문에 **456MB**입니다.
- vector 색인은 원소 하나(4KB + 이웃 목록)가 8KB 페이지 하나를 차지해 m을 늘려도 크기가 같았습니다(약 8,190바이트/권). halfvec은 약 2,730바이트/권.
- 합계: vector = 표 456MB + 색인 664MB = **1.12GB**, halfvec = 232MB + 221MB = **453MB**. 운영 디스크 여유 9.2GB에는 둘 다 들어갑니다.

앞 40개(분명한 책 질문)만 쓴 빠른 시험(`pg-results-quick.json`, m16 ef_c64)에서는 재현율이 더 높았습니다: k 120 ef_search 200 vector 0.944 / halfvec 0.946, k 10 ef_search 100 0.99. **짧고 모호한 질문(「고양이」「음...」)에서 HNSW가 많이 놓칩니다**(점수가 고르게 퍼져 그래프 탐색이 갈피를 못 잡음). 전수 비교는 정의상 재현율 1.0입니다.

읽는 법:
- **`hnsw.ef_search`가 120보다 작으면 결과가 ef_search 줄 수만큼만 나옵니다**(40 → 40줄, 100 → 100줄). 서버가 120줄을 원하므로 ef_search ≥ 120이거나 `iterative_scan`을 켜야 합니다. `relaxed_order`는 결과 순서가 조금 어긋날 수 있는데, 서버는 순서(RRF 순위)를 씁니다.
- halfvec은 vector와 재현율이 같고 조금 빠르며 크기는 1/3입니다. 바꾼다면 halfvec입니다.
- 재현율 0.87(m16, ef_search 200)은 「정답 상위 120 중 평균 약 16권을 놓친다」는 뜻입니다. 이것이 최종 추천 8권에 미치는 영향은 재지 않았습니다.

### 3-5. 네트워크·JDBC 몫

- Windows의 psycopg → WSL 도커(55432)로 잰 「클라이언트 시간」은 모든 질문에 약 44ms가 더 붙었습니다. `select 1`은 0.45ms인데 벡터 글자 하나(약 11KB)를 보내기만 하는 `select $1::vector(1024) is not null`이 44.0ms — Windows↔WSL 중계의 지연(지연 ACK 류)이지 Postgres 시간이 아닙니다. 그래서 위 표는 DB 시간을 씁니다.
- 같은 질문을 컨테이너 안 psql(Unix 소켓, `\timing`)로 보내면 halfvec m16 ef_search 200 k 120이 **중간값 12.66 / p90 15.94 / p99 18.37ms**(두 번째 12.56ms)로, EXPLAIN의 11.55ms보다 약 1ms 많습니다. 운영처럼 백엔드와 DB가 같은 도커 네트워크면 전송·파싱 몫은 약 1\~2ms [추정]입니다. JDBC로 1,024개 숫자를 보내는 몫은 따로 재지 않았습니다.

| 300MB (색인보다 조금 큼, Postgres 몫 포함하면 부족) | 89.5 / 136.5 / 421.8ms | 78.8 / 104.9 / 127.1ms |
| 200MB (색인보다 작음) | 224.2 / 295.0 / 366.0ms | 202.3 / 269.9 / 324.0ms |

→ 색인이 메모리에 다 있지 않으면 HNSW는 지금의 전수 비교(운영 97ms)보다 **느려집니다**. 운영 서버는 2GB에 백엔드 힙만 640MB이고 `shared_buffers`는 64MB라, 색인은 OS 페이지 캐시에 기대야 합니다.

## 4. 30만·100만 권 (추정)

| 책 수 | 전수 비교 PC (잰 값, 반복 데이터) | 전수 비교 운영 [추정, ×1.46] | 힙 [줄 × 1,036바이트] | halfvec 표 + 색인 [권당 2,862 + 2,730바이트] | vector 표 + 색인 [권당 5,623 + 8,190바이트] | halfvec m16 색인 만들기, PC 2코어 [n·log n 비례] |
|---|---|---|---|---|---|---|
| 81,078 | 66.4ms | 97ms (잰 값) | 81MB (잰 값) | 453MB (잰 값) | 1.12GB (잰 값) | 76초 (잰 값) |
| 300,000 | 274.9ms | 약 400ms | 약 311MB | 약 1.68GB (색인 0.82GB) | 약 4.1GB (색인 2.46GB) | 약 5분 |
| 1,000,000 | 715.7ms | 약 1,050ms | 약 1,036MB (-Xmx640m 초과) | 약 5.6GB (색인 2.73GB) | 약 13.8GB (디스크 여유 9.2GB 초과) | 약 19분 |

- HNSW 질문 시간은 책 수에 거의 로그로 늘어 색인이 메모리에 있으면 30만·100만 권에서도 PC 기준 10\~30ms일 것 [추정]. 다만 같은 재현율을 지키려면 ef_search를 더 올려야 할 수 있고 [추정], 무엇보다 **색인 0.82\~2.73GB가 캐시에 있어야** 합니다(3-6절). 지금 2GB 서버로는 불가능하고, DB를 4GB 이상 서버로 옮기거나 키워야 합니다 [추정].
- 전수 비교 쪽의 다른 길(재지 않음): `nearest`를 Java Vector API로 바꾸거나 2스레드로 나누면 몇 배 빨라질 수 있습니다. 데이터·재현율·운영 구성을 바꾸지 않는 길이라 HNSW보다 먼저 볼 만합니다.

## 5. 사용자 주장 확인

| 주장 | 확인 |
|---|---|
| 벡터는 DB에서 약 330MB, 색인은 따로 | 원자료 float32는 332MB로 맞음. 실제 `vector(1024)` 표는 **456MB**(TOAST), 색인 **664MB** 추가 → 1.12GB. `halfvec`이면 232MB + 221MB = 453MB |
| HNSW는 근사라 재현율을 다시 재야 함 | 맞음. k 120에서 m16/ef_search 200 0.865\~0.869, m32/ef_search 400 0.975, 짧은 질문은 최저 0.04\~0.6. ef_search < 120이면 결과 줄 수부터 모자람 |
| 실제 시간은 잰 적 없음 | 이번에 잼: 전수 비교 PC 66.4ms(운영 로그 97ms), HNSW DB 시간 2.9\~57ms(설정별), Postgres 순차 스캔 286\~394ms |

## 6. 권고

**지금은 전수 비교 유지.** 숫자로:

1. 시간 이득이 작습니다. 운영 nearest 97ms → HNSW로 약 12ms + 전송 1\~2ms [추정, 색인이 캐시에 있을 때]. 첫 글이 나오기까지 약 1.7초(`1-how-it-works.md` 예시 로그 `llm-first=1700`)에서 최대 약 85ms를 줄이는 정도입니다.
2. 대신 답이 바뀝니다. 같은 120권을 주는 설정이 없습니다(최고 0.975, 그때 DB 시간 38\~57ms로 이득 거의 없음).
3. 운영 2GB 서버에서는 색인(halfvec 211MB, vector 633MB)이 캐시에서 밀리면 80\~220ms로 지금보다 느립니다.
4. 디스크 0.45\~1.1GB와 색인 다시 만들기(가져오기마다 76초\~4분, 운영은 더 김)가 늘어납니다.

**다시 볼 때:** 책이 약 15만\~20만 권이 되어 운영 nearest가 200ms를 넘거나 힙이 약 170MB를 넘을 때 [추정]. 그 전에 Java 쪽 가속(Vector API, 2스레드)을 먼저 재 보고, 그래도 HNSW로 간다면 `halfvec(1024)` + `halfvec_ip_ops` + m 16, ef_construction 64, `hnsw.ef_search` ≥ 200, 색인 전체가 들어갈 RAM(30만 권이면 약 1GB 여유)의 DB 서버를 함께 정합니다. 그때 질문 222개(`questions.txt`) 재현율과 최종 추천이 달라지는 비율을 다시 잽니다.
