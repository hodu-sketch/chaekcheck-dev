## 1. 책 벡터 한 벌 (I-10)

### 지금 상태
| | 책첵 추천 | AI 검색 |
|---|---|---|
| 벡터 원본 | PC `<data>/ml/pool-100000-intro.npy` + `<data>/ml/foryou-100k/vectors.npy`(추천목록 2,010권, 10-26 다시 만듦) | PC에서 만든 `book-vectors.bin`(int8, 81,078권, 추천목록 책은 10-25의 `<data>/ml/foryou/vectors.npy`) |
| 운영에 있는 것 | 벡터 없음. 이웃 표 `foryou.book_neighbour`만 | `book-vectors.bin`을 백엔드 메모리에 올림 |
| 계산 | 책 × 책 코사인을 미리(PC) | 요청마다 질문 벡터 × 책 벡터 코사인 |

두 결과물(이웃 표, `book-vectors.bin`)은 쓰임이 달라 앞으로도 따로 있어야 함. 합치는 것은 **PC의 원본 벡터**를 한 벌로 하는 것.

### 왜
- **같은 책은 어디서나 같은 벡터여야** 추천 이웃, AI 검색 질문 벡터 비교, 분류기, 군집이 서로 맞음. 지금은 추천목록 책 약 2천 권이 두 벌에서 다름(0절). 효과는 정리(한 번만 계산, 바뀐 책만 다시 계산) 정도이고 추천 품질을 직접 올리지는 않음
- 다시 만들 때 **무엇이 바뀌었는지** 알아야 함: 소개 글이 수집으로 늘면 그 책만 다시 계산

### 방법 [안]
- **책 벡터 저장소 한 곳**(PC 데이터 폴더, 운영에는 필요한 형태로만): 책마다 `book_id, 모델(nlpai-lab/KURE-v1), 글 규칙 판(제목·저자·출판사·연도 + 소개 앞 300자), 글 해시, 벡터(float16), 가져오기 export_id`
- 글 해시가 같으면 다시 계산하지 않음(이어 만들기). 책 번호가 바뀌는 다시 가져오기에서는 글 해시로 옛 벡터를 찾아 재사용
- 쓰는 곳마다 내보내기만 다르게: 이웃 표(20권), AI 검색 `book-vectors.bin`(int8), 분류기·군집 입력(float32)
- 10만 권 밖으로 넓히기는 시간 때문에 따로 판단: 소개를 넣으면 이 PC CPU로 1,000권에 475초 [실측, 사전 시험] → 134만 권 약 177시간. 24 세션의 ONNX int8 모델로 속도를 다시 재고 [확인 필요], 사용자에게 물음(plan 요청)
- 134만 권이면 정확한 전체 비교(8만 × 8만은 PC에서 수 분)가 어려워짐 → 근사 이웃 검색(faiss의 HNSW·IVF)을 쓰고 **정확한 이웃과 겹치는 비율(recall@20)**을 잼 [확인 필요: faiss-cpu 버전·라이선스는 plan 조사(1.15.1, MIT)]

### 시험
| 시험 | 합격선 [안] |
|---|---|
| 같은 책·같은 글에서 새 벡터와 옛 벡터 코사인 | ≥ 0.9999(같은 모델·같은 글이면 같아야 함). int8 내보내기는 최악 0.9997 이상(24 세션 실측 0.99975) |
| 이웃 표 겹침: 새 저장소로 만든 이웃 20권 vs 지금 운영 이웃 | 글이 같은 책에서 평균 ≥ 19/20 |
| AI 검색 회귀: 24 세션의 평가 묶음(질문 72·80개)을 새 벡터로 | "맞음" 비율이 흔들림 범위 안 |
| 근사 검색(134만 권으로 넓힐 때) | recall@20 ≥ 0.95, 한 권 찾기 시간 기록 |

## 2. 책 프로필을 지도학습으로 (I-11)

### 왜
- Haiku로 책마다 만들면 비용이 책 수에 비례하고(10만 권 배치 3종 34.34달러), 10만 권 밖은 비어 있음
- 0절대로 **벡터만으로 이웃 다수결이 분야 70%·확신 높은 절반 89%**를 맞힘 → 학습한 분류기는 더 낫고, 확신이 낮은 책만 Haiku에 보내면 비용이 "애매한 책 수"에만 비례
- 24 세션 선례: 질문 분류를 같은 KURE 벡터 위 작은 신경망으로 바꿔 Haiku 97.8% 대비 94.5%(학습 자료를 고르게 준 뒤) — 단 처음에 드문 유형이 1% 미만이라 58.5%였음. **불균형이 성패를 가름**

### 데이터 다루기 [안]
1. **정답 정리**: Haiku 프로필 77,551권(새 50,324 + 앞 27,227)을 한 형식으로. 사전 밖 값은 빈칸(수집 세션이 379개 고침)
2. **누수 막기**: 같은 작품 묶음(지금 규칙 + 2-4의 쌍 분류기)을 **통째로** 학습·검증·시험 중 한 곳에만 둠(group split). 0절대로 같은 작품이 6,924권이라 무시하면 점수가 부풀려짐
3. **나누기**: 작품 묶음 단위 층화 70/15/15. 시험 묶음은 끝까지 보지 않음
4. **잡음 다루기**: 같은 작품끼리 분야가 다른 20.8%는 "어느 쪽이 맞나"가 아니라 **경계가 애매한 책**이 많다는 뜻 → ① 사람이 확인한 **금 표준 300권**(층화 추출, 사용자 또는 Sonnet 두 번 일치 + 사용자 검토)을 따로 두고 Haiku 자체의 정확도도 같이 잼 ② 3절의 오류 찾기로 고친 정답으로 다시 학습
5. **입력**: KURE 벡터(1,024). KDC는 입력에 넣지 않음 — 3절 오류 찾기에서 **독립된 의견**으로 써야 하므로(넣으면 같은 정보를 두 번 셈) [안]
6. **불균형**: 칸별 가중치(class_weight balanced)와 작은 칸 묶기. 50권 미만 작은 칸은 분류기 대상에서 빼고 Haiku

### 모델 [안]
| 칸 | 방법 | 이유 |
|---|---|---|
| 큰 분야(22) | 다항 로지스틱 회귀 → 모자라면 은닉층 1개 MLP | 1,024차원 선형 분리가 잘 됨(이웃 다수결 70%), 해석·보정 쉬움. MLP는 24 세션 1차 모델과 같은 틀 |
| 작은 칸(121) | 큰 분야별로 따로 학습(계층), 50권 미만 칸 제외 | 칸이 큰 분야 안에서만 뜻이 있음 |

**방법 [안]** — 신호 셋 중 **둘 이상**이면 의심(plan 안과 같음):
1. **이웃 투표**: 이웃 20권 다수 분야와 다름(학습 없이 바로, 0절 다수결과 같은 계산)
2. **교차 예측(confident learning)**: 작품 묶음 단위 5겹으로 나눠 **자기가 학습에 안 쓰인 겹**의 예측 확률로, "예측이 자신 있게 다름"을 찾음. 도구 cleanlab의 `find_label_issues` [확인 필요: 작업 시 문서, plan 조사 2.9.0 Apache-2.0]
3. **KDC**: KDC가 있는 책(약 49%)에서 KDC 강목 → 분야 대응과 다름. 대응표는 데이터로 만들되 최다 일치가 60% 미만인 강목은 신호에서 뺌(1류처럼 갈리는 곳)

**시험**:
| 지표 | 방법 | 합격선 [안] |
|---|---|---|
| 의심 책 수, 신호별·조합별 | 그대로 셈 | 보고 |
| **의심의 정밀도** | 의심 200권 + 의심 아닌 100권을 섞어 방식을 가리고 Sonnet(또는 사용자)이 판정 | 의심 쪽 실제 오류율이 의심 아닌 쪽의 3배 이상 |
| 고친 뒤 효과 | 고친 정답으로 다시 학습 → 금 표준 정확도 | 오르거나 같음 |

### 3-2. 사전에 없는 주제 찾기 (군집, I-13)

**왜**: 분류 사전(22·121칸)은 사람이 정한 것. 실제 책에 많은데 사전에 없는 무리(예: 반려동물 에세이)는 군집으로만 보임. 이 무리가 꼬리표 후보.

**방법 [안]**:
1. 차원 줄이기(UMAP, 1,024 → 5~15) 뒤 **HDBSCAN**(최소 무리 크기 30~50, 잡음은 따로). 이유: 무리 수를 미리 안 정해도 되고 잡음을 버릴 수 있음(k-means는 모든 책을 억지로 넣음). scikit-learn에 HDBSCAN이 있음 [확인 필요: 버전]
2. 무리마다 **대표 낱말**(c-TF-IDF: 무리 안 소개 글을 한 문서로 보고 TF-IDF). 한국어는 형태소 분석이 필요 [확인 필요: 쓸 분석기(kiwi 등)·라이선스]. 이 흐름을 묶은 도구가 BERTopic(미리 만든 벡터를 넣을 수 있는지 [확인 필요])
3. **후보 고르기**: 무리 안 프로필 분야가 한 칸에 몰리지 않거나(순도 < 0.6), 「기타」가 많거나, 같은 작은 칸 안에서 따로 뭉친 무리
4. 무리 이름은 사용자가 붙임(LLM은 무리당 한 번 제안까지, plan 요청)

**시험**:
| 지표 | 왜 | 합격선 [안] |
|---|---|---|
| 잡음 비율, 무리 수, 크기 분포 | 쓸 만한 덩어리인지 | 잡음 < 40%, 무리 수 50~400 |
| 순도(프로필 분야 기준)·조정 랜드 지수 | 사전과 얼마나 겹치나(너무 겹치면 새 정보 없음) | 보고 |
| **안정성**: 씨앗 3개로 다시 돌려 무리 대응 ARI | 우연한 무리를 걸러냄 | ARI ≥ 0.7인 무리만 후보 |
| 대표 낱말 응집도(NPMI) | 낱말이 한 주제를 가리키나 | 보고, 하위 20% 제외 |
| **사람이 이름 붙일 수 있는 비율** | 결국 꼬리표가 되려면 | 후보 무리의 ≥ 70% |

### 3-3. 책 묶음 (같은 작품 I-14, 주제 묶음)

**같은 작품 묶음 — plan 안을 바꾸자고 제안**: plan은 "벡터가 아주 가깝고 저자 같음"을 제안했지만, **같은 작품 쌍의 코사인이 0.68~0.78로 보통 이웃과 같았음**(2026-10-26 실측, 「돈키호테」·「십팔사략」·「명상록」). 벡터 거리 문턱만으로는 못 가름.
- 대신 **쌍 분류기** [안]: 후보 쌍(이웃 20권 안 + 같은 저자)마다 특징 = 제목 글자 n-gram 유사도, 정리한 제목 포함 여부, 첫 저자 일치·포함, 코사인, 출판사 같음, 출간 연도 차, ISBN 앞자리 → 로지스틱 회귀
- 정답: 지금 규칙이 잡는 쌍(양성) + Haiku 「같은 작품」 판정 쌍(10-26 판정 1,000쌍) + 사용자가 확인한 쌍. 시험: 방식 가린 300쌍, **정밀도 ≥ 0.95**(잘못 묶으면 다른 책이 추천에서 사라지므로 정밀도 우선), 재현율 보고. 효과는 10-26과 같은 판정(250쌍 중 같은 작품 5 → ?)

**주제 묶음**: 3-2 무리를 칩·"안 본 분야 한 권"에 씀. 효과는 기존 오프라인 표(분야 고르기, 판정)로.

## 4. 운영 지표와 A/B (I-05, I-06)

### 지금 할 수 없는 것 [실측]
- 7일 방문 키 22개(방문 키 = 탭을 열 때 만든 난수라 같은 사람도 탭마다 다름), 운영 회원 1명, 책첵 추천 화면 보기 누적 88회(대부분 출시일 시험). 책 열기 비율 30%에서 **5%p 차이를 가리려면 한 쪽에 약 1,300번 보기**, 도서관 누름 5%에서 2%p면 약 1,900번(유의 5%, 검정력 80%)이 필요 → 지금 트래픽으로는 수년
- 그래서 **A/B를 바로 하지 않고, 쌓일 준비부터** 함

### 순서 [안]
1. **기록 더하기(바로 가능, 사이클 26 뒤 코드)**
   - 노출 기록: 책첵 추천을 열 때 보인 책 번호와 자리, 출처(개인·기본·다시 보여 주기·다른 분야), 칩 — 이것이 없으면 클릭률도, 나중의 오프라인 재생 평가도 불가
   - `library_click`의 화면에 책첵 추천 구분(지금은 추천도서 전체가 `picks`), 칩 누름
   - 개인정보: 이용 기록에는 이미 로그인 회원 번호와 탭 단위 방문 번호가 남음(ADR-0134, 1년, 탈퇴 때 회원 번호 비움). 노출 기록도 같은 규칙(같은 표·같은 보관)으로 둘지, 처리방침 문구가 덮는지 plan이 정함 [확인 필요: plan]. 운영 회원은 2026-10-29 현재 1명이라 회원 기록 기반 맞춤·A/B도 아직 표본이 없음
2. **오프라인 평가를 주 지표로 유지**: 지금 표(맞힘·가상 사용자·방식 가린 판정)를 바꿀 때마다
3. **끼워 넣기(team-draft interleaving)**: A·B 두 방식의 결과를 한 목록에 번갈아 섞어 보여 주고, 사용자가 누른 책이 어느 쪽 것인지 셈. 같은 사람이 두 방식을 동시에 보므로 A/B보다 훨씬 적은 표본으로 방향을 가림 [확인 필요: 필요한 표본은 트래픽이 생긴 뒤 측정]
4. **A/B(트래픽이 생긴 뒤)**: 배정은 브라우저 키 해시(세션마다 바뀌지 않게), 표본 비율 검사(SRM), 주 지표 = 책첵 추천 방문당 도서관 누름(대출 의사), 보조 = 책 열기·10초 머묾, 안전 지표 = 빈 목록 비율·응답 시간. 기간은 최소 2주(요일 효과)
5. **오프라인과 온라인 맞추기**: 운영 지표가 쌓이면, 오프라인 판정 점수 차이가 실제 누름 차이와 같은 방향인지 확인 — 맞으면 오프라인 시험을 계속 믿고, 아니면 판정 기준을 고침
