# 책 설명 모으기 요약: 사이클 26에서 풀어낸 문제 다섯

## 이 문서가 답하는 것 / 답하지 않는 것

- 답하는 것: 처음 보는 사람을 위해, 책 설명(요약·표지·분류)을 한 곳으로 모으면서 부딪힌 문제 다섯 가지. 문제마다 「무슨 일이 있었나 → 왜 → 어떻게 고쳤나 → 결과 숫자 → 어떻게 확인했나」. 숫자는 모두 잰 값이고 원기록은 [plan-feedback](../../cycles/plan-feedback.md) 「# 사이클 26」입니다.
- 답하지 않는 것: 단계별 진행·파일 위치·운영 기록 → [2-dev-record.md](2-dev-record.md). PostgreSQL 실행 계획의 자세한 계산 → [3-postgres-generic-plan.md](3-postgres-generic-plan.md). 질의 9판 비교 → [4-keyword-query-speed.md](4-keyword-query-speed.md).

## 배경

책첵에는 책 요약, 표지, 분류(책 프로필), AI 책 찾기용 검색 글이 기능마다 따로 있었습니다. 추천목록, 책첵 추천, AI 책 찾기, 책 상세 화면이 각자 다른 표를 읽어서, 같은 책인데 화면마다 요약이 다르게 보일 수 있었습니다. 사이클 26은 이것을 책 정보를 맡는 `catalog` 모듈 한 곳으로 모으고, 표지 그림을 서버 디스크에서 AWS S3로 옮긴 작업입니다. 그 과정에서 아래 다섯 문제를 풀었습니다.

## 1. 서버를 오래 켜 두면 AI 책 찾기가 느려지던 문제 (v1.20.1)

**무슨 일이 있었나.** 배포 뒤 AI 책 찾기 응답 시간을 다시 재니, 서버를 켠 직후 두 번은 괜찮다가 세 번째부터 낱말 여러 개짜리 질문(「소설 말고 위로가 되는 책」)의 낱말 찾기 단계가 3\~5.4초 걸렸습니다.

**왜.** 같은 SQL을 여러 번 쓰면 데이터베이스가 쓰는 방식이 바뀌기 때문이었습니다.
- Java의 PostgreSQL 드라이버는 같은 SQL을 한 연결에서 5번 쓰면, 그 SQL을 서버에 「준비된 문장」으로 올려 두고 다시 씁니다.
- PostgreSQL은 준비된 문장을 몇 번 실행한 뒤, 실제 값을 보지 않고 세운 「일반 실행 계획(generic plan)」이 더 싸 보이면 그것으로 바꿉니다.
- 이 질의에서는 값을 모르니 「'%소설%'에 맞는 책이 얼마나 될지」를 정해진 기본값(0.5%)으로 짐작했고, 맞는 책을 **8권**으로 예상했습니다. 실제로는 **16,418권**이었습니다(약 2,000배 차이).
- 8권이라 믿은 계획은 모든 책마다 「이 책을 가진 내 도서관 수」를 처음부터 세는 방식이었고, 1만 6천 권에 그걸 하느라 5초가 걸렸습니다. 값을 보고 세운 계획은 점수 순으로 먼저 줄 세운 뒤 위쪽 606권만 세서 0.24초였습니다.
- 옛 표에서도 같은 일이 일어나는 것을 확인해, 이번 배포가 만든 문제가 아니라 전부터 숨어 있던 문제임을 알았습니다.

**어떻게 고쳤나.** 이 질의 하나만 실행할 때 「값을 보고 계획을 세워라」(`SET LOCAL plan_cache_mode = force_custom_plan`)를 먼저 실행합니다. `SET LOCAL`이라 이 질의가 끝나면 원래대로 돌아가고 다른 질의에는 영향이 없습니다. 드라이버나 DB 전체 설정을 바꾸지 않은 까닭은, 다른 질의에서는 일반 실행 계획이 오히려 이득이기 때문입니다.

**어떻게 확인했나.** 같은 검색을 12번 한 뒤 일반 실행 계획이 한 번도 쓰이지 않았는지 보는 자동 시험을 만들었고, 고침을 빼면 이 시험이 실패하는 것도 확인했습니다. 운영에서는 같은 질문 24개를 4번씩 연달아 돌려 1초 넘은 낱말 찾기가 0번이었고, 느린 10%의 첫 글이 5.2\~5.8초에서 2.76\~3.05초가 됐습니다. 계산 과정 전체: [3-postgres-generic-plan.md](3-postgres-generic-plan.md).

## 2. DB 변경이 배포를 5분 막던 문제: 295초 → 4.2초

**무슨 일이 있었나.** 책 설명 표 다섯을 옮기는 DB 변경(Liquibase)을 운영과 같은 크기의 복사본에서 미리 돌려 보니 295초가 걸렸습니다. 이 동안 서버가 뜨지 않으므로, 그대로 배포하면 서비스가 약 5분 멈춥니다.

**왜.** 단계를 나눠 재니 데이터를 옮기는 INSERT는 합쳐 9초였고, 옮긴 뒤 한글 요약 68,414줄의 통계를 만드는 `ANALYZE`가 388초였습니다. 한글 글을 사람이 읽는 순서(en_US.utf8)로 비교하며 통계를 만드는 비용이었습니다.

**어떻게 고쳤나.** 요약 칸은 정렬해서 보여 줄 일이 없어 바이트 순 비교(`COLLATE "C"`)로 바꿨습니다(→ ANALYZE 0.06초). 검색 표의 색인은 데이터를 다 넣은 뒤에 만들게 했습니다.

**결과.** 복사본에서 4.2초, 운영 배포에서 7.7초(226,038줄). 옮긴 다섯 표의 줄 수와 글이 옛 표와 모두 같은 것을 비교해 확인했습니다.

## 3. 같은 책 요약을 네 화면에서 하나로

**무슨 일이 있었나.** 추천목록, 책첵 추천, AI 책 찾기 카드, 책 상세가 요약을 서로 다른 표에서 읽어 같은 책에 다른 글이 보일 수 있었습니다.

**어떻게 고쳤나.** 요약·표지·분류·AI 검색 글을 `catalog` 모듈의 표와 공개 API 한 곳으로 모으고, 네 화면이 모두 그 API를 읽게 했습니다. 다른 모듈은 이 표를 직접 읽지 않습니다(Spring Modulith 모듈 경계). 추천목록에만 요약이 있던 774권은 새 요약을 미리 만들어 채웠습니다.

**어떻게 확인했나.** 운영에서 「달러구트 꿈 백화점」의 요약이 네 API에서 글자까지 같았고, 다른 책 11권도 책 상세와 모두 같았습니다.

## 4. 표지 113만 장을 서버 디스크에서 S3로

**무슨 일이 있었나.** 표지는 운영 서버 디스크(남은 공간 약 9GB)에 두고 서버가 직접 보냈습니다. 전체 표지 약 113만 장을 올리기엔 디스크도 서버 부담도 맞지 않았습니다.

**어떻게 고쳤나.** 비공개 S3 버킷과 CloudFront로 옮기고, 웹은 CloudFront 주소에서 그림을 받습니다. S3에는 PC만 올리고 운영 서버에는 S3 권한을 주지 않았습니다. 순서는 「그림을 먼저 다 올리고, 올라간 그림만 책과 연결」이라 깨진 그림이 보일 일이 없습니다.

**숫자.** 폴더 하나씩 올리면 초당 약 25장이었고, 8묶음으로 나눠 동시에 올려 초당 약 170장이 됐습니다(256폴더, 실패 0). S3에 올라간 1,130,143개와 연결할 1,128,687장을 대조해 빠진 것 0을 확인한 뒤에야 책과 연결했고, 표지 있는 책이 80,091권에서 1,145,754권이 됐습니다.

## 5. 흔한 낱말 하나로 찾을 때 더 빠르게 (v1.20.3, v1.20.4)

**무슨 일이 있었나.** 1번을 고친 뒤 남은 가장 느린 경우는 「소설」처럼 흔한 낱말 하나만 묻는 질문이었습니다(운영 253\~347ms). 맞는 책 1만 2천 권의 점수가 모두 같아, 모든 책의 「내 도서관 수」를 세야 했기 때문입니다.

**어떻게 했나.**
- 「내 도서관 수 세기」를 PostgreSQL 확장(intarray)의 배열 교집합 함수로 바꾸는 등 질의를 8가지로 고쳐 만들고, 낱말 6가지 × 도서관 수 3\~4가지 경우마다 재고, 답이 모두 같은지 결과의 해시로 확인했습니다.
- PC에서 가장 좋았던 판을 운영에 올린 뒤 같은 도구로 다시 재니, 도서관 1,000곳 이상을 쓰는 사용자의 여러 낱말 질문 6가지가 11\~42ms 느려진 것을 찾았습니다. 실행 계획을 보니 기존 질의는 위쪽 606권만 세고 새 질의는 1만 6천 권을 모두 세기 때문이었습니다.
- 그래서 경우를 나눴습니다. 낱말이 하나이거나 도서관이 500곳 이하면 새 방식, 아니면 기존 방식.

**결과.** 운영 24가지 경우 합 2,773 → 2,006ms(−28%), 가장 느린 경우 343 → 204ms(−41%), 전보다 10ms 넘게 느려진 경우 0, 답은 모두 같음. 전체: [4-keyword-query-speed.md](4-keyword-query-speed.md).
