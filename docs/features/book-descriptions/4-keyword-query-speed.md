# 4. AI 검색 낱말 찾기 더 빠르게: 여러 판을 여러 경우로 재고 고른 기록

## 이 문서가 답하는 것 / 답하지 않는 것

- 답하는 것: v1.20.1 뒤에도 남은 「흔한 낱말 질문의 낱말 찾기 0.25~0.35초(운영)」를 줄이려고 질의를 9판(V0~V8)으로 만들어 여러 경우에서 잰 숫자, 답이 바뀌지 않는지 확인한 방법, 판마다 빠르고 느린 까닭(실행 계획), 운영에 처음 올린 판(V7, v1.20.3)이 일부 경우 느려져 고친 판(V8, v1.20.4), 운영 결과.
- 답하지 않는 것: v1.20.1의 generic plan 문제 → [3-postgres-generic-plan.md](3-postgres-generic-plan.md). 요약 → [1-summary.md](1-summary.md) 5절. AI 검색 전체 흐름 → [../aisearch/1-how-it-works.md](../aisearch/1-how-it-works.md) 4-7절.

## 1. 무엇을 줄이려 했나

낱말 찾기 질의(`catalog.internal.texts.JdbcAiSearchIndex.find`, SQL은 [3-postgres-generic-plan.md 3-1절](3-postgres-generic-plan.md))는 맞는 책을 찾는 데는 수십 ms면 되는데(pg_bigm 색인, 「소설」 12,200권 9ms), 그 뒤 맞은 책마다 두 가지를 계산한다.

1. `plan_count`: 책의 도서관(평균 79곳)이 계획 도서관(최대 2,455곳)에 몇 곳 드는지. v1.20.1까지 `(SELECT count(*) FROM unnest(library_ids) l WHERE l = ANY(plan))` — 상관 서브쿼리(SubPlan)로 책마다 배열을 펼쳐 하나씩 비교.
2. `score`: 낱말마다 `search_text LIKE '%낱말%'`를 SELECT에서 한 번 더 계산(WHERE에서 이미 확인한 것).

「소설」처럼 흔한 한 낱말 질문은 맞은 1만 2천 권이 모두 점수 1로 같아, 순서를 정하려면 모든 책의 `plan_count`를 세야 한다. 운영에서 이 경우가 253~347ms로 가장 느렸다(4-2절).

## 2. 판

| 판 | `plan_count` | `score` |
|---|---|---|
| V0 (v1.20.1·v1.20.2 운영) | `unnest` + `= ANY` SubPlan | `LIKE` 다시 |
| V1 | `intarray.icount(intarray._int_inter(library_ids, plan))` 식 그대로 | `LIKE` |
| V2 | V1 | `strpos(search_text, 낱말) > 0` |
| V3 | V0 | `strpos` (확장 없이 되는 판) |
| V4 | `(SELECT intarray.icount(…))` 스칼라 서브쿼리 | `LIKE` |
| V5 | V4 | `strpos` |
| V6 | SQL 함수 `catalog.plan_library_count_sql` (COST 1000, `SET` 절로 인라인 막음, 측정용) | `strpos` |
| V7 (v1.20.3 운영) | PL/pgSQL 함수 `catalog.plan_library_count` (COST 1000) | `strpos` |
| **V8 (v1.20.4 운영)** | **한 낱말이거나 계획 도서관 500곳 이하 → V7의 함수, 아니면 V0의 SubPlan** | **`strpos`** |

- intarray: PostgreSQL 기본 확장(contrib). `_int_inter`는 두 정수 배열을 정렬해 교집합을 만들고(C 함수), `icount`는 원소 수. 우리 DB 이미지(postgres-bigm)에 들어 있음.
- `strpos(글, 낱말) > 0`은 `LIKE '%낱말%'`(낱말 안 `%` `_` `\`를 이스케이프한 것)과 같은 책을 고른다: 둘 다 「글 안에 이 글자들이 그대로 있나」이고, `search_text`는 `COLLATE "C"`라 바이트 비교. WHERE는 그대로 `LIKE`(pg_bigm 색인을 타야 하므로).

## 3. 잰 방법

- 도구: [`scripts/aisearch/eval/bench_keyword_query.py`](../../../scripts/aisearch/eval/bench_keyword_query.py). psql로 판마다 한 번 데운 뒤 5번 재어 중앙값(psql `\timing`), 모두 `plan_cache_mode = force_custom_plan`(서버와 같음). `--forms=V0,V8`로 판을 고름.
- 경우 = 낱말 6가지 × 계획 도서관 4가지(1,000곳은 v1.20.3 뒤에 더함).
  - 낱말: 흔한 한 낱말(「소설」, 12,200권), 드문 한 낱말(「커피」), 두 낱말(소설·위로), 세 낱말(경제·투자·초보), 다섯 낱말(다이어트·식단·자세히·다룬·건강), 두 낱말 + 핵심어(에세이·여행, 핵심어 여행).
  - 계획 도서관: 표에 나오는 모든 도서관 2,455곳 / 앞 1,000곳 / 앞 200곳 / 앞 30곳.
- **답이 같은지**: 경우마다 결과 30줄(`book_id:score:plan_count`, 순서대로)의 md5를 판끼리 비교. **잰 모든 경우 × 모든 판에서 같았다**(PC 18경우 × 8판, 운영 24경우 × V0·V7).
- 어디서: 내 PC의 연습 DB(c26 `db`, 운영과 같은 가져오기 14번, `catalog.book_search` 76,759줄)와 운영 DB(읽기만). PC와 운영의 플래너 설정(`cpu_operator_cost`, `parallel_setup_cost`, `max_parallel_workers_per_gather` 2, `work_mem` 4MB …)은 같아 같은 계획을 고르고, 운영(t4g.small, 2코어)이 약 2배 느리다.
- 원본(git 밖): dev `data/c26/bench-keyword-pc*.tsv`, `bench-keyword-prod-before.tsv`, `bench-keyword-prod-after2.tsv`, `bench-keyword-prod-v8.tsv`.

## 5. 왜 판마다 다른가 (실행 계획)

| 판 | 플래너가 고른 계획 (2,455곳 / 두 낱말) | `plan_count` 계산 횟수 | 한 번 비용 |
|---|---|---|---|
| V0 | Parallel Bitmap Heap Scan → 작업자별 Sort(점수) → Gather Merge → **Incremental Sort** | **606번**(LIMIT에 필요한 묶음만) | 약 21µs(상수 배열 → 해시 비교, 단 `unnest`·집계 노드 비용) |
| V1·V2 | Bitmap Heap Scan(직렬) → Sort | 16,418번 | 약 7µs |
| V7 | Parallel Bitmap Heap Scan(작업자에서 계산) → Sort → Gather Merge | 16,418번(작업자 둘이 나눔) | 약 10µs(2,455개 계획 배열을 함수 호출마다 복사·정렬 확인) |

- 플래너는 함수 비용을 선언된 `COST`(× `cpu_operator_cost` 0.0025)로 본다. intarray C 함수는 COST 1이라 「싸다」 → 모든 줄을 직렬로 계산(V1·V2). COST 1000(줄마다 2.5)이면 작업자 병렬로 모든 줄을 계산(V7). V0의 SubPlan은 줄마다 6.33으로 보여, 모든 줄 계산(약 12만)보다 Incremental Sort로 필요한 줄만 세는 계획이 싸다.
- **흔한 한 낱말**: 점수가 모두 같아 어떤 계획이든 모든 줄을 센다 → 한 번이 싼 V7(병렬, 10µs)이 V0(21µs)보다 빠름(운영 347 → 208).
- **여러 낱말 + 큰 계획**: V0은 606번만 세는데 V7은 16,418번 센다. 계획 배열이 클수록 V7 한 번이 비싸져(2,455개 배열을 매번 다룸) V0이 이김. 작은 계획(200곳 이하)에선 V7 한 번이 아주 싸 모두 세도 이김.
- **COST를 바꿔 보기**(PC): 1,000 / 3,000 / 10,000 → 합 640 / 669 / 799ms. 비용을 올려도 플래너가 Incremental Sort 계획으로 돌아가지 않고 느려지기만 해 1,000으로 둠.
- **strpos**: 점수 계산에서 `LIKE` 패턴 매칭 대신 부분 문자열 찾기. 낱말이 많을수록 차이가 남(운영 2,455곳 / 다섯 낱말 V0 143 → V3 121).

## 6. 고른 판: V8 (v1.20.4)

- 규칙: **한 낱말이거나 계획 도서관이 500곳 이하면 V7의 함수, 아니면 V0의 SubPlan. 점수는 늘 strpos.** 500은 잰 200곳(함수가 이김)과 1,000곳(SubPlan이 이김) 사이 값이고 그 사이는 재지 않았다 [안].
- 운영 숫자로 고른 각 칸이 4-2절 표에서 굵게 한 쪽이다. PC(18경우): 합 V0 1,248 → V7 887 → **V8 821ms**, 가장 느린 경우 154 → 82 → **76ms**, **V0보다 10ms 넘게 느린 경우 0**, 답 모두 같음.
- 구현:
  - `catalog/003-intarray.yaml`(v1.20.3): `CREATE SCHEMA intarray` + `CREATE EXTENSION intarray WITH SCHEMA intarray`. **public이 아닌 따로 된 스키마**: intarray는 `integer[]`용 `&&` `@>` `<@` 연산자를 새로 만드는데, 검색 경로(public)에 있으면 다른 질의의 기본 배열 연산자 자리를 차지할 수 있어서. 이름을 붙여서만 부른다(시험이 public에 intarray `&&`가 없음을 확인).
  - `catalog/004-plan-library-count.sql`(v1.20.3, formatted SQL `runOnChange`): `catalog.plan_library_count(integer[], integer[])` PL/pgSQL, `IMMUTABLE STRICT PARALLEL SAFE COST 1000`.
  - `JdbcAiSearchIndex`(v1.20.4): `planCountFor(낱말 수, 계획 도서관 수)`가 `PLAN_COUNT`(함수)와 `PLAN_COUNT_LAZY`(SubPlan) 중 고름, `FUNCTION_PLAN_MAX = 500`. 점수와 핵심어 점수는 `strpos(search_text, :wN) > 0`.
  - 시험: `AiSearchIndexTests.planLibraryCountIsTheIntersectionOfTheTwoArrays`(순서 섞인 배열, 빈 배열, public에 intarray 연산자 없음), `bothPlanCountsGiveTheSameOrder`(같은 책들을 계획 10곳(함수)과 600곳(SubPlan)으로 찾아 같은 순서), 기존 순서·`%` `_`·generic plan 시험.
- 배열에 같은 도서관이 두 번 들어 있으면 intarray는 한 번, V0은 두 번 센다. `book_search.library_ids` 76,759줄 중 중복 있는 줄 0(`catalog.book.library_ids`에서 복사, 연습 DB 확인).

## 8. 배운 것

- PC에서 고른 판이 운영(코어 수가 적은 서버)에서 일부 경우 느려질 수 있다: PC 측정에서 작게 보인 차이(15ms)가 운영에서 42ms가 됐다. 운영에서 같은 도구로 다시 재고 나서야 「계획 크기 × 낱말 수」에 따라 갈린다는 것이 보였다.
- 플래너의 비용 선언(`COST`)은 계획 모양을 바꾸지만 원하는 모양(필요한 줄만 세기)으로 늘 유도되지는 않는다. 그래서 질의 쪽에서 경우를 나눴다.
